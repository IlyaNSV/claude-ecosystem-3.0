>

> - `CHANGELOG.md` — release notes (что вошло в версию)
> - `ROADMAP.md` — план фаз
> - `.product/.decisions/journal.md` — журнал решений для **пользовательских** продуктовых проектов, которые ведутся через Ecosystem 3.0 (когда dogfooding запустится — для самой Ecosystem 3.0 тоже появится свой `.product/`)

>
> **Что записываем:**
> - Архитектурные решения с rationale (почему X вместо Y; какие альтернативы отвергнуты)
> - Баги → root cause → fix → lesson

>
> **Что НЕ записываем:**
> - Рутинные commit-level правки (git log)
> - User stories / фичи (нет такого — экосистема сама продукт)
> - Личные заметки (используй NOTE-* когда dogfooding запустится)
>
> **Формат записи:** см. шаблон в конце документа.
>
> **Теги в использовании:** `#architecture`, `#bug-fix`, `#scope-change`, `#spec-revision`, `#pilot-finding`, `#refactor`, `#tooling`, `#ux`.

## DEC-DEV-0221 — R0 исполнен: термин «Release DoD» в каноне RL + опциональная 6-категорийная body-секция (soft)

### Decision

Mini-readiness (паттерн `readiness-gate.md`, 3 решения под уже ратифицированными D1/D3 из DEC-DEV-0216):

## DEC-DEV-0222 — Онбординг-пак хост-сессии (кондуктор): прогрев L0-L2 из живых файлов + правило coverage-check интенций владельца

**Date:** 2026-07-19
**Trigger:** запрос владельца: (1) «загрузка всегда актуального онбординга по экосистеме» в выбранную хост-сессию, управляющую VM-сессиями (длинные сессии, мало собственного контекста; разово до 20% окна допустимо, + указатели для дообучения); (2) правило «прежде чем строить по моему предложению — проверь, покрыта ли интенция AS IS».
**Tag:** #global-loop #host-console #knowledge-plane #onboarding #process-triggers

### Decision

**Coverage-check самой интенции (первое применение нового правила):** покрыто частично — K0-лестница добора (CONDUCTOR.md §Knowledge plane, ратифицирована 0216) + работающие механизмы context-map/rails дайджестов и генерируемых каталогов; guide-хаб (0130) — онбординг для человека. НЕ покрыто: разовый префетч выбранной хост-сессии одним действием с бюджет-контролем. Построена именно дельта.

**(1) `dev/meta-improvement/scripts/host-onboard.cjs`** (zero-deps, read-only, tolerant): сборка пака в stdout из ЖИВЫХ файлов при каждом запуске — шов+план global-loop, `factory-conductor/CONDUCTOR.md`, хартии host-console/release-dod, `INFORMATION-MAP.yaml`, генерируемые каталоги (команды+глоссарий), гейты+fabric, VM-грабли (память `env_vm_claude_factory` + глобальный скилл `vm-factory-ops`, с капами) + секция deepdive — L3-указатели «когда понадобится → открой». Заголовок несёт три закона (ответ без SSOT-указателя = не ответ; version-skew; «пак отстаёт — статус верифицируй git+журналом») и бюджет-таблицу секций; `--list`/`--only`/`--skip`/`--budget` (дефолт-cap 40k ток. ≈ 20% окна — потолок владельца; фактический дефолт-состав ~38k). Ничего не пишется на диск — это НЕ зеркало доков (K0 «резолвером и генерацией, не пересказом» соблюдён: пак и есть генерация on-demand). Отвергнуто: SessionStart-хук с env-гейтом (выбор «эта сессия — кондуктор» и так явный акт владельца; команда честнее авто-инжекта и не жжёт окно обычных сессий — event-gated, вернёмся, если ручной запуск начнут забывать); статический ONBOARDING.md-файл (копия = дрейф); включение в пак 08-skills и 00-concepts (скиллы исполняют VM-сессии, тезис/пайплайн уже авто-инжектится context-map дайджестом — вынесены в deepdive ради бюджета).

**(2) Правило coverage-check** — строка в SSOT-таблице «Process triggers» CLAUDE.md: на предложение владельца об изменении/улучшении экосистемы — ДО дизайна карта «интенция ↔ что уже есть» (rails + INFORMATION-MAP + grep + deferred/tech-debt + хвост журнала; объёмное — recon-субагенту), покрыто/частично/нет с указателями. Rationale владельца дословно: «я быстрее развиваю экосистему, чем успеваю запомнить, что именно я создал»; аналог ITP для improvement-запросов, цель — общее понимание соотношения интенции и фактической реализации, не бюрократия (тривиальные правки — не триггер).

**Impact:** Волна 0 получает штатный прогрев сессии-кондуктора (PLAN.md §1-bis дополнен, SEAM.md «Состояние» актуализирован — включая догон факта «R0 исполнен» из PR #229, который шов не отражал); новые предложения владельца проходят AS IS-проверку по правилу таблицы. Декларация доступов сверх обязательных чтений шва (v3): recon-субагент по репо (инвентаризация онбординг-механизмов + размеры файлов), grep/чтение DEV_JOURNAL (0216, 0221), `ls dev/global-loop`, прогоны собранного скрипта.

**Addendum (2026-07-19, та же единица) — авто-активация: env-гейт хук + слэш-команда (запрос владельца после сдачи v1).** Ручной запуск оставлен, добавлены два пути: **(а)** SessionStart-хук `dev/meta-improvement/hooks/host-onboard-session-start.js` — fires только при `CONDUCTOR_SESSION=1` (обычные сессии — тихий exit 0); ветвление по `source`: startup/clear → полный цикл, compact → короткое напоминание-указатель, resume → тишина; регистрация в `.claude/settings.local.json` (локальная — файл не коммитится, JSON-сниппет в шапке хука); **(б)** проектная слэш-команда `/host:onboard` (`.claude/commands/host/onboard.md`, прецедент трекинга — `/meta:audit-smoke`). **Ключевой конструктивный факт (добор через claude-code-guide, docs hooks.md):** лимит вывода хука ~10k символов, Bash-тул режет ~30k — полный пак (~178KB) через них не проходит ⇒ оба пути переведены на паттерн **«пак → temp-файл → императив Read»** (`--out [файл]` в скрипте, дефолт `%TEMP%/claude-host-onboard-pack.md`; Read без обрезки, пак 1557 строк < 2000-строчного дефолта Read). ## DEC-DEV-0223 — курс Tech-Uplift: PLAN+VISION расширенного стека (PROPOSED)

**Date:** 2026-07-19
**Trigger:** заказ владельца после ландшафтного ресерча 2026-07-19 (27 решений, адверсариальные пробы уникальности): план заимствования сильных сторон корпуса + vision выхода функциональных блоков за пределы Claude Code; north-star дословно — «реальный AI PMO с отличным качеством работы». Интейк-развилки закрыты владельцем: стек = гибрид-ядро + control-plane + EoS по фазам («подобрать под процессы, функции и правила наиболее подходящую и надёжную инфраструктуру»); архитектура — ЕДИНАЯ с Кондуктором; аппетит — сразу структурный переход.
**Tag:** #tech-uplift #vision #architecture #landscape-research

### Decision

Созданы `dev/tech-uplift/VISION.md` + `dev/tech-uplift/PLAN.md` (status: PROPOSED — ратификация владельцем при merge; исполнение волн — отдельными единицами).

**Coverage-check (первое полноформатное применение правила DEC-DEV-0222, recon-субагент по 9 под-интенциям) перевернул несущий ход плана:** вместо greenfield-рантайма — **генерализация уже построенного оркестраторного ядра** (`orchestrator/lib/fabric-engine.cjs` — event-sourced ndjson + materialized + bit-for-bit replay; `autonomy-policy.cjs` — чистая gate-функция с уроком 0201; `run-ledger.cjs`) в пакет `pmo-core` + ровно три чистые ниши без фундамента в репо: eval-фреймворк скиллов, собственный MCP-интерфейс методологии, token circuit-breaker. Валидатор артефактов оказался ПОКРЫТ сильнее ожиданий (44 правила + artifact-validate.js + validation-runner + check-validation-sync) — заимствование MoAI-линтера сужено до JSON Schema-проекции + fixture-тестов (кандидат v1.1 backlog) + роста automation-покрытия.

**Ключевые выборы и отвергнутые альтернативы:**
- **Гибрид, не ре-хостинг.** Premise-check тезиса «CC уже не про мои задачи» (по [[feedback_substrate_premise_verification]]): подтверждён точечно — CC не подходит там, где LLM-слою поручена работа рантайма (гарантии/состояние/счётчики/параллелизм); слой суждений (D1/D2, ресерч) остаётся в CC. Полный уход с CC ОТВЕРГНУТ (цена огромна, выгода нулевая). Критерий выноса функции формализован: детерминизм ∨ межсессионность ∨ межхарнессность, доказуемо.
- **MCP-интерфейс вместо немедленного EoS.** Межхарнессность на уровне интерфейса за ~20% цены; полный EoS (GSD-класс, capability-registry + адаптеры) — Волна 4, trigger-gated (публикация ∨ второй харнесс). ОТВЕРГНУТ немедленный EoS.
- **Единая шина событий с Кондуктором.** Контракт события проектируется ДО кода обеих сторон (T1.3), совместим с планируемым `events.jsonl` global-loop Волны 3; второй event-store ОТВЕРГНУТ (два источника истины = дрейф по построению). Вклады в Кондуктора (Convoy-чекпойнты, ready/blocking-очередь, TCB) адресуются в существующие волны global-loop, H-фазы — только по «го» владельца; standalone control-plane в экосистеме ОТВЕРГНУТ (дублирует дом 0216).
- Прочее отвергнутое с причинами — PLAN §1 (GUI, крипто-witness, Bayesian promotion, preference-learning, свайп-контроль).

**Impact:** у трека появился дом `dev/tech-uplift/`; Волна 1 = экстракция ядра → схемы артефактов → event-контракт+state → FSM фаз (self-strict/shipped-soft ландшафта — наш же диагноз: продуктовый workflow до сих пор на промптах) → CLI+MCP; гейт волны — смоук на пилоте, soft-миграции по канону §6. Ресерч-связка: выжившая уникальность («тройка» D1-глубина + handoff + code-enforcement) усиливается ровно этим слоем.

**Lesson (в копилку 0222):** coverage-check отработал по назначению с первого боевого применения — recon нашёл готовое ядро там, где план собирался строить с нуля, и сузил 2 из 9 заимствований до дельт. Цена — один sonnet-recon (~3 мин); сэкономленное — недели дублирующей стройки. Правило «интенция ↔ что уже есть» подтверждено как обязательный вход крупного дизайна.

## DEC-DEV-0225 — P8 `user-journey-acceptance`: браузерная приёмка user-journey как обязательный этап перед `done`

**Date:** 2026-07-22
**Trigger:** решение владельца — в приёмку встраивается финальное тестирование с реалистичной имитацией пользователя (браузерный user-journey), как обязательный этап перед `done`. Инструмент ядра одобрен после ресерча.
**Tag:** #architecture #orchestrator #process-fabric #acceptance #pilot-finding

### Context — почему P7-зелёный ≠ «работает»

Живой прецедент на пилоте (RUN-2026-07-17-A, первый релиз RL-001): P6 `GO`, P7 `READY_TO_SMOKE`, деплой `DEPLOYED` и `/health` 2xx — **а первое касание пользователя было битым** (пост-логин 404, нет домашней страницы). ## DEC-DEV-0228 — Анализ эффективности Global Loop: экосистема эффективна ровно настолько, насколько её правила материализованы в машине

**Date:** 2026-07-29
**Trigger:** «Го» владельца на исполнение `dev/global-loop/EFFECTIVENESS_ANALYSIS_PLAN.md` (ratified 2026-07-28) отдельной аналитической сессией + уточнение «продолжай автономно до owner class решений». Вопрос владельца дословно: «насколько эффективен мост от интенции через хост-пульт → механизмы экосистемы → фактические изменения в коде… нет ли такого, что экосистема переусложняет или переписывает одно и то же по 10 раз… кодовая база может деградировать, хотя комплексные процессы "по бумагам" работают».
**Tag:** #architecture #tooling #pilot-finding #measurement

### Context

Два живых прогона (RUN-A 17–20.07, RUN-B 22–23.07) и эпоха до них дали корпус, который ни разу не измерялся: 203 сессии, 14 573 вызова инструментов, 610 коммитов пилота, 1109 сообщений владельца, 91 запись машинного run-ledger, 24 релиза. Замеры M1–M15 посчитаны по пре-регистрированным формулам (`analysis/PREREG.md`), M16 (каузальная A/B-проба) не запускался — требует отдельной санкции.

Ключевая методологическая рамка: **самоотчёты — объект проверки, а не источник истины**. Поэтому первым выполнен M7.

### Options considered

1. **Верить журналу и считать по нему** — отвергнуто рамкой плана: ландшафтный базлайн даёт до 8× завышения самоотчётов.
2. **Считать всё по harvest-копиям на хосте** — отвергнуто санитарией: harvest **не содержит субагентов** (1463 файла, 201 MB), а на них приходится 27–67% токенов. Любой учёт по harvest занижен в разы.
3. **Считать по полному корпусу VM + git + run-ledger, а самоотчёт верифицировать выборочно** — выбрано.

### Decision

Отчёт и датасет — `dev/global-loop/analysis/` (карта — `analysis/README.md`, главный документ — `analysis/REPORT.md`).

### Outcome

**Опасения владельца проверены, два из трёх не подтвердились:**
- «переписывает одно и то же по 10 раз» — **нет**: ни один артефакт не переписан >3 раз, проходы сходящиеся; self-churn 13.2% → 3.0% → 1.3% (индустрия ≈7.9%); дубли 1.5% → 1.4%; плотность ветвлений 0.106 → 0.108 при +38% кода;
- «база деградирует при зелёных бумагах» — **нет**: подгонки под гейт не найдено (2 подозрительных эпизода за всю историю, оба добросовестные), fix survival 74/74, mutation score 0.778;
- «сложная фабрика — маленький выхлоп» — **частично да**: цена runtime-строки выросла 198 → 613 → 1099 токенов, но природа работы сменилась (стройка → доводка), а темп поставки вырос впятеро; «фабрика пишет доки вместо кода» **опровергнуто**: markdown:код 3.38:1 → 0.16:1.

**Что подтвердилось как реальная проблема:**
- **у 97 из 162 дефектов (59.9%) не существует гейта, который обязан был поймать**; среди 61 открытого — 77% этого класса;
- **rework** 22.9% сессий / 21.1% токенов (строго), до 55.4% токенов (широко); крупнейший источник — гейт-петля RUN-A, где **пять вердиктов NO-GO имели один механический корень, продиагностированный пятикратно, каждым агентом заново**;
- **оверхед пульта**: токены хоста / токены исполнителей = 1.62 (RUN-A) → 0.47 (RUN-B) при пороге 0.20; **мультипликатор всего 1.8 ч машинной работы на 1 ч владельца**;
- **cost per resolved intent = 802 616 токенов / 92 мин**, но между прогонами упал в 3.4 раза (1.55M → 457k);
- 4 интенции переоткрывались, **3 из них — одна тема «приёмка не ловит базовых ошибок»**.

### Lessons

1. **Главный вывод, к которому независимо сошлись три замера: работает то, что материализовано в машине.** M10 — сильные оси спек это те, у которых есть обязательный носитель в шаблоне (провалена ровно одна ось — матрица доступа, у которой носителя нет, и именно из неё пришли находки #3/#4/#9). M11 — не дрейфуют **вообще** только `requirements`, единственный артефакт-вход кодогенерации; всё остальное устаревает за ~16 дней. Дефект-реестр — где гейт есть, он ловит (46 машиной против 15 владельцем), где гейта нет — 60% дефектов. **Правило, записанное в реестр, но не превращённое в гейт, возвращается тем же дефектом.**
2. **Метрика харнесса `totalTokens` — это пиковый контекст, а не расход.** Заявленные «1.81M токенов консилиума» оказались суммой water-mark; фактический расход — 24.5M (в 9.4 раза больше). Любые бюджетные оценки, снятые с этого поля, занижены на порядок. Считать расход только по `message.usage` каждой assistant-записи.
3. **Многоагентный консилиум проиграл одиночному судье** по совпадению с тем, что владелец ратифицировал (4/6 против 5.5/6) при цене 24.5M токенов. Причина не в многоагентности, а в агрегаторе: он читает только оценки и выбрасывает раздел «риски рекомендации», где присяжные честно записали дисквалифицирующий факт.
4. **Наивный аудитор самоотчётов производит ложные обвинения** с частотой, сопоставимой с той, что ищет: первые прогоны верификатора дали 4 «расхождения», все оказались дефектами метода (регекс `GO` внутри `NO-GO`, номера артефактов как счёт прогона, поиск следа не в субагентах, единственная форма записи счёта). Аудировать аудитора нужно **до** объекта.
5. **Инвентарь свидетельств обязан покрывать все репозитории, где живёт работа.** Три независимых судьи указали на одно слепое пятно (пакет видел только коммиты пилота); после расширения 10 из 14 спорных вердиктов сместились — все в сторону **большего** успеха.

## DEC-DEV-0229 — M16: канон не выиграл у стороннего конвейера, но проиграл ровно там, где у него нет носителя принуждения

**Date:** 2026-07-29
**Trigger:** Отдельное «го» владельца на исполнение M16 — единственного каузального замера плана `EFFECTIVENESS_ANALYSIS_PLAN.md` (§7). Дословная интенция: «дадим экосистеме и просто claude … на одинаковом репо одинаковые команды для создания рабочего MVP … Главное, чтобы исполнитель не понимал, что его экспериментируют». По ходу исполнения — второе указание владельца: «свои ошибки попутно классифицировать и записывать, чтобы потом пересмотреть их и распределить по артефактам и enforcement».
**Tag:** #architecture #measurement #pilot-finding #process

### Context

DEC-DEV-0228 закрыл ретроспективу выводом «экосистема эффективна ровно настолько, насколько её правила материализованы в машине», но честно пометил: все выводы корреляционные, эпохи различались задачами и моделями. M16 устраняет это прямым способом — одна задача, одна спецификация (`.product/` на границе D2-B), одна модель (Opus 4.8 high), одна машина, побайтно одинаковое задание; **единственная переменная — методологический слой**.

Решением владельца контроль усилен против пререги: вместо «Claude Code + MCP» плечо B получило **GSD Core 1.8.0 + 7 проверенных MCP-серверов**. Добор из сети (Informed Fetch) опроверг нашу же ландшафтную оценку 19.07 «GSD BROKEN»: архивирован лишь старый репозиторий, проект живёт как `open-gsd/gsd-core`, релиз v1.8.0 от 22.07. То есть сравнивался **наш канон против зрелого стороннего канона**, а не против голого агента.

### Options considered

1. **Оценивать по самоотчётам сессий** — обе объявили «MVP готов, всё зелёное». Отвергнуто: анти-ловушка №1 плана, самоотчёт завышает успех.
2. **Только скриптовая приёмка** — объективно, но не различает «сделано иначе» и «сделано хуже». Взято как основа, но недостаточно.
3. **Только слепое судейство** — ловит качество, но подвержено position bias и не воспроизводимо. Отвергнуто как единственный канал.
4. **Оба канала + правило реверса + калибровка харнесса** — принято. Скрипт решает всё, что решается детерминированно (план §9.1); судье уходит только неразрешимое скриптом; каждая ось засчитывается лишь при совпадении обоих порядков предъявления.

### Decision

Приёмочный набор (12 сценариев с якорями в `SC/VC/BR/IC`) **закоммичен до старта плеч** (`8698490`), рубрика судейства — до вердиктов, харнесс **откалиброван на заведомо рабочей реализации** (копия пилота на HEAD) до применения к плечам.

**Результат: канон измеримого выигрыша не дал.** `pass²` 7/12 против 6/12 (все четыре прогона побайтно воспроизводимы, флаки-поведения ноль), слепое судейство **2:2** при двух неопределённых осях, затраты выше на 11% по токенам и 26% по времени — в пределах объявленного порога «сигнал начинается с разов». Гипотеза H1 не подтвердилась ни в одной половине.

**Но различие ошибок систематично, и это главное.** Канон выиграл оси **«инварианты»** и **«проверяемость»** — ровно то, что материализовано в его шаблонах (спека обязана перечислить IC и VC). Контроль выиграл **«точность числовых правил»** и **«честность самоописания»** — ровно то, что принуждает фазовый цикл GSD с его реестром решений. Канон промахнулся там, где носителя нет: усечённое расписание авто-повторов (пауза 60 с недостижима при README, обещающем 15/30/60) и длительность видео, принимаемая **со слов клиента**, из-за чего обходимы сразу два числовых порога спеки — 180 минут и trial-cap 30 минут. Оба дефекта найдены двумя судьями независимо.

### Consequences

- **Тезис DEC-DEV-0228 подтверждён четвёртым независимым замером — и впервые не в ретроспективе.** Работает то, у чего есть носитель принуждения; не работает то, что оставлено дисциплине. Теперь это видно на контролируемом сравнении, где оба конвейера сильны каждый в своей материализованной части.
- **Два дешёвых носителя-кандидата в очередь следующей волны** (внесены в `analysis/REPORT.md` §7.6): (1) гейт сверки числовых констант кода с их BR-источником — механически скриптуемо; (2) обязательный раздел «отступления» в артефакте сдачи — контроль выиграл ось честности не умом, а формой.
- **Обнаружен пробел в чеклистах D7:** есть `blind-comparison-protocol.md` про слепоту судьи, но нет чеклиста про **слепоту исполнителя** — «что видит исполнитель» (история git, remote, соседние каталоги, пользовательский уровень, область MCP, запущенные эталоны, исходящие зависимости стенда, куда реально ложится запись). Две мои ошибки (ERR-04, ERR-05) родились ровно в этом пробеле и обе были пойманы случайно, а не процедурой.
- **`vm-factory-ops` §0 неполон:** `docker compose up` не числится разрушающим действием, хотя для одноимённого проекта именно им является — compose опознаёт ресурсы по имени ПРОЕКТА, и `up` в клоне снёс контейнеры рабочего пилота (ERR-01).
- Ограничения объявлены и не заминаются: n=1 на плечо; канон **июньской** версии (без P8/DoD/I-8) — нижняя оценка сегодняшней экосистемы; эффект прогретого окружения у второго плеча; A6/A7 непроходимы при хешировании токенов; не мерилось ничего за пределами одного захода.

### Lessons

1. **Калибруй измерительный прибор на заведомо рабочем объекте до применения.** Харнесс на первом прогоне дал 3/12 на реализации, прошедшей приёмку прошлых прогонов, — и все девять провалов оказались его собственными (не дожидался результата отправки формы; искал контрол языка только среди `select`; не находил кнопку без `type=submit`; писал не в ту БД). Без калибровки я получил бы правдоподобные числа, не относящиеся к плечам.
2. **Реверс порядка у судьи — не формальность.** Он перевернул **2 оси из 6**. Без него первый судья дал бы «4:2 за канон», второй — «4:2 за контроль», и любое из этих чисел выглядело бы результатом.
3. **Пишущий харнесс обязан начинать с канареечной записи** и сверки целевой БД. Приложение может проксировать `/api/*` на адрес по умолчанию — так приёмка писала в базу рабочего пилота (ERR-06). Правило, встроенное в код после этого, поймало следующую же ошибку (ERR-07) до начисления единого балла: **в коде ловит, намерением — нет.**
4. **Стенд из `git clone` несёт всю будущую историю.** `git show` отдавал готовую реализацию тех же FM. Строить контрольные стенды из `git archive` + свежий `git init`.
5. **`pass^k` как ловушка на флаки не сработала — ловить было нечего.** Все четыре прогона побайтно совпали. Полезный побочный факт: обе реализации детерминированы, и различие между ними — не шум прогона.
6. **Ошибки исполнителя замера стоит вести реестром по ходу** (указание владельца). Семь записей с классификацией дали два конкретных кандидата в enforcement — больше, чем дал бы разбор по памяти в конце.

1. **Пятое независимое подтверждение теоремы трека, теперь на самом операторе:** из всех ошибок заезда сбежала ровно та, что была заявлена прозой без машинной проверки (CNT-005), и повторилась ровно та, у которой не было носителя (ctx-перегруз — дважды за заезд, «дожмёт, осталось чуть-чуть»). 2. **Класс «строгий парсер против живого форматирования»**: 2 из 3 DoR-гэпов P8 оказались слепотой парсеров к вариациям (`jneg*` vs `neg-*`, `| **SI-1** |` vs `| SI-1 |`) — при вводе hard-гейтов первый живой прогон закономерно чинит форматы, не поведение; это цена канонизации, платится один раз.
3. **Forensics-паттерн «субагентам верить можно»**: у DA/validate-субагентов свежие контексты — их сырые выводы из transcripts служат ground truth для проверки синтеза перегруженной main-петли; расхождение main↔агент = детектор деградации.

## DEC-DEV-0240 — UJA_HEADED: человеко-визуальный канал приёмки P8 как ОПЦИЯ, а не как новый дефолт

**Date:** 2026-08-05
**Trigger:** Волна B трека vm-observability (решение владельца). Интенция трека дословно: «мне главное своими глазами увидеть кто, как и что проверял в браузере, что вводил, какие кнопки нажимал… будто тестировщик снимал рабочий стол во время проходов по сценариям» + «следил в режиме реального времени или пересматривал видеозаписи постфактум, чтобы быть автономнее».
**Tag:** #orchestrator #observability #gates #tooling

### Context

P8 `user-journey-acceptance` уже гоняет реальный браузер по журнеям — но headless и без записи: `grep video|recordVideo orchestrator/` давал 0 совпадений, а wiring-тест жёстко принуждал слово HEADLESS в промпте (шов трека фиксировал это как «headed = дельта → DEC-DEV»). То есть единственное место экосистемы, где машина реально «ходит по продукту руками пользователя», не оставляло ни одного кадра, который владелец мог бы посмотреть. Слой 3 трека (`SEAM.md`) был gated на CSS-имплементацию пилота; владелец открыл его отдельным «го».

Ограничения на входе: (а) headless-дефолт — канон, который нельзя ломать; (б) канонический `playwright.config.*` целевого проекта — контракт проекта, не наша собственность; (в) ратифицированный инвариант «два канала» (`CONDUCTOR.md §Наблюдаемость`): машинный канал принимает решения из событий/отчётов, человеко-визуальный только ДОПОЛНЯЕТ и никогда не становится входом авто-решения; (г) harness-ограничение DEC-DEV-0073 §D.1 — Workflow-скрипт не имеет доступа к Node API, входы идут через `args`.

### Options considered

1. **Headed/видео по умолчанию** (просто снять слово HEADLESS) — **отвергнуто**. Дефолт, требующий X-сервера, ломается ровно там, где гейт важнее всего: CI, ssh-прогон, любая машина без десктопа. Приёмка обязана работать без человека у экрана; наглядность — режим, а не предусловие. Плюс видео стоит диска и времени на каждом прогоне, включая те, что никто не смотрит.
2. **Мутировать `playwright.config.*` целевого проекта** (дописать `use.video='on'` перед прогоном) — **отвергнуто**, и это ключевой отказ. Гейт, редактирующий конфигурацию, под которой он же судит, — тот же класс, что «подложить скриншот, чтобы закрыть visual-дыру» (DEC-DEV-0237): свидетельство подгоняется под желаемый результат. Плюс правка живёт в git пилота и переживает прогон. Взамен — ОДНОРАЗОВЫЙ override-конфиг рядом с артефактами, который ИМПОРТИРУЕТ канонический и мержит только `use: { video, trace, screenshot }` (`--video` в CLI Playwright нет — именно поэтому нужен файл, а не флаг).
3. **Отдельный процесс/скилл «визуальный прогон»** — отвергнуто: второй драйвер тех же журнеев = второй источник правды о том, что именно проверено; расхождение вопрос времени. Наглядность — режим существующего P8.
4. **Скан видео с диска (`test-results/**/*.webm`)** — отвергнуто: (а) убивает чистоту `parse` (N разборов одного отчёта обязаны быть байт-идентичны), (б) подметает артефакты ЧУЖИХ прогонов в том же outputDir и выдаёт их за свидетельство этого. Пути берутся из `attachments[]` самого отчёта — единственного источника, который знает, чья запись.
5. **Тумблер только через env / только через args** — отвергнуто оба по отдельности. Env — то, что просил владелец (оператор на VM включает для ЭТОГО прогона, не редактируя args), но §D.1 не обещает наличия `process` в песочнице харнесса, и env-only рисковал оказаться мёртвым при запуске из Workflow. Args — родной канал харнесса, но это не тот тумблер, который просили. Взято оба: `ENV.UJA_HEADED === '1'` за `typeof process !== 'undefined'`-гардом ИЛИ `args.headed`.

### Decision

`UJA_HEADED=1` (или `args.headed`) переключает P8 в человеко-визуальный режим: видимый браузер на десктопе VM (`DISPLAY`, по умолчанию `:0`, переопределяется `UJA_DISPLAY`) + Playwright `video`/`trace` через override-конфиг. Промпт форкается ровно в одном месте — ветка `HEADED ? … : …`, где `else`-арм БАЙТ-В-БАЙТ прежняя headless-команда (проверено программно на диффе против `origin/main`: эмитируемая строка совпадает, 470/470 символов). `uja-report.cjs parse` аддитивно отдаёт `video_files[]` / `trace_files[]`, собранные из `attachments[]` отчёта; порядок и семантика существующих полей не тронуты (их читает run-ledger). Записи называются в `reasons` → едут в `disclosures` → в `run.json` (там `disclosures` в `TRAIL_KEYS`, а `video_files` — нет).

Что режим НЕ делает, и это принуждено тестом: не входит в вычисление вердикта (`ujaResult`/`finalResult` не видят `HEADED`), не разрешает пересматривать PASS/FAIL по картинке, не даёт ре-ран «ради красивого видео». Недоступный дисплей — деградация в headless С СОХРАНЁННЫМ видео + явное disclosure, а не тихий отказ (Playwright пишет видео и headless — видео и headed это разные вещи, что в дизайне легко перепутать). Headed-прогон, вернувший НОЛЬ видео, объявляется сломанным каналом вслух — и не меняет вердикт.

### Outcome

Правки в 4 файлах (`user-journey-acceptance.mjs`, `uja-report.cjs`, оба теста); `uja-report` 46→55 проверок, wiring 22→26, `npm run test:orchestrator` EXIT=0. Живой headed-прогон на VM НЕ выполнялся — это следующий шаг Волны B (нужен пилот со стилями, предусловие Шага 2 NEXT-HORIZON) и он же единственная настоящая валидация: сейчас принуждена структура, не поведение реального Playwright на VM. `video_files` осознанно НЕ добавлен в `run-ledger.TRAIL_KEYS` (вне scope правки) — записи находятся через `artifacts_dir` + disclosure-строку; если понадобится машинный доступ к списку из `run.json`, это отдельная однострочная дельта.

### Lessons

1. **«Сделать видимым» ≠ «сделать видимым по умолчанию».** Наглядность — режим, который включает человек, когда смотрит; дефолт обязан выживать там, где человека нет. Ровно поэтому же наблюдаемость не имеет права стать предусловием приёмки.
2. **Гейт не редактирует то, под чем судит.** Правка канонического конфига пилота ради видео — тот же класс, что подложенный скриншот из 0237; форма отказа (импортирующий override рядом с артефактами) переносится на любой будущий «включить опцию инструмента на один прогон».
3. **Свидетельство берут из отчёта, а не с диска.** Скан выходной директории смешивает прогоны и приписывает чужую запись своему вердикту — та же ошибка атрибуции, что «зелёный healthcheck = рабочий журней», только на уровне артефактов.
4. **Env-тумблер в harness-скрипте — гипотеза, а не факт.** §D.1 обещает отсутствие Node API; читать `process.env` без `typeof`-гарда значит менять «тумблер не сработал» на «весь гейт упал с ReferenceError». Два канала (env для оператора, args для харнесса) стоят одной строки и снимают вопрос.
## DEC-DEV-0241 — Hook-команды абсолютизированы через ${CLAUDE_PROJECT_DIR} в exec-форме: принуждение, которое умело молча умирать от смены cwd

**Date:** 2026-08-05
**Trigger:** Пилот `my-first-test` — 39 падений хуков за одну сессию 2026-08-04/05 (три разных хука, два разных cwd), ни одного видимого сообщения владельцу.
**Tag:** #bug-fix #pilot-finding #architecture #enforcement

### Context

Хук-записи в `settings.json` пользовательских проектов генерировались **прозой** в двух местах (детерминированного генератора нет): `commands/ecosystem/bootstrap.md` Step 6b и `commands/ecosystem/update.md` Step 6. Обе прописывали относительную команду `node .claude/hooks/<module>/<file>`.

Тройное совпадение превращает это в худший из возможных отказов:

1. **Относительный путь.** Резолвится от cwd процесса хука.
2. **Persistent cwd сессии.** Хук-процесс запускается «в текущей директории» — не в корне проекта. Как только модель делает `cd` в подкаталог, cwd сессии уезжает, и `.claude/hooks/...` перестаёт резолвиться. Документация харнесса прямо предупреждает: плейсхолдер существует, чтобы ссылаться на скрипт «regardless of the working directory when the hook runs»; утверждения «cwd == корень проекта» в документации **нет**.
3. **Non-blocking.** Почти все хуки экосистемы warn-only / fail-open. `Cannot find module` уходит в stderr, exit-код никого не гейтит.

Итог: **принуждение отключает себя само, тихо**. Владелец видит зелёную сессию; 39 раз подряд не сработали валидатор артефактов, каскад-чек и session-state. Это ровно тот класс, против которого построена вся волна носителей (DEC-DEV-0228/0229: «работает то, у чего есть носитель принуждения») — носитель был, но у него был отключаемый молчанием провод.

Конвенция `process.env.CLAUDE_PROJECT_DIR || process.cwd()` уже устоялась **внутри тел** 5 хуков (`journal-hook`, `scope-guard`, `lesson-gate`, `lesson-presence-gate`, `worktree-enter-guard`) — то есть правильная идея была найдена, но не дотянута до **команды запуска**. Тело хука не выполняется, если процесс не стартовал.

### Options considered

Форма — несущее решение, поэтому взята не из приоров, а верифицирована по актуальной документации харнесса (`code.claude.com/docs/en/hooks.md`, `hooks-guide.md`) recon-субагентом с требованием цитат и URL.

1. **`node "$CLAUDE_PROJECT_DIR/.claude/hooks/<module>/<file>"`** (shell-форма, кавычки вокруг всего пути) — **отвергнуто.** Shell-форма на Windows идёт через Git Bash, а при его отсутствии — через **PowerShell**; раскрытие `$CLAUDE_PROJECT_DIR` под PowerShell в документации не описано **вообще** (в PowerShell env-переменная читается как `$env:VAR`, так что `$CLAUDE_PROJECT_DIR` схлопнулся бы в пустоту → `node /.claude/hooks/...` → то же молчаливое падение, просто на другой платформе). Плюс такой формы кавычек нет ни в одном примере доки — там кавычат только сам плейсхолдер (`"$CLAUDE_PROJECT_DIR"/rest/of/path`).
2. **`cd "$CLAUDE_PROJECT_DIR" && node .claude/hooks/...`** — отвергнуто по той же причине (shell-форма ⇒ тот же PowerShell-провал), плюс лишняя зависимость от семантики `&&`.
3. **Exec-форма: `command: "node"` + `args: ["${CLAUDE_PROJECT_DIR}/.claude/hooks/<module>/<file>"]`** — **принято.** Прямые основания из документации: «Prefer exec form for any hook that references a path placeholder»; «There is no shell… No shell tokenization happens on any platform»; плейсхолдеры «substituted into `command` and into each `args` element as plain strings» — то есть подстановку делает **сам харнесс, а не шелл**, что полностью снимает платформенный разрыв; «The `node` plus script-path pattern works on every platform because `node.exe` is a real binary» (в отличие от `.cmd`/`.bat`-шимов). Троублшутинг доки формулирует это как прямое лекарство: «If you see "command not found", use absolute paths or `${CLAUDE_PROJECT_DIR}`… To avoid shell quoting entirely, add `"args": []` to switch to exec form».

**Что подтвердить не удалось (фиксирую честно, а не замалчиваю):** доки больше не называют `CLAUDE_PROJECT_DIR` *абсолютным* путём — только «the project root»; версия введения плейсхолдера в CHANGELOG харнесса не найдена. Остаточный риск exec-формы — **версионный пол**: сборка Claude Code, не знающая поля `args`, увидит `command: "node"` без скрипта. Принят сознательно: это направление развития документации, а альтернатива меняет версионный риск на **постоянный платформенный** разрыв.

### Decision

Обе прозаические генерации переведены на exec-форму **синхронно** (рассинхрон bootstrap↔update — уже случавшийся класс, DEC-DEV-0198/DEF-CTX-3).

Неочевидное следствие, которое пришлось спроектировать отдельно: **в exec-форме `command` у всех хуков экосистемы одинаков — `"node"`**. Поэтому:

- **Классификация владения переехала в `args[0]`.** Регекс `^\$\{CLAUDE_PROJECT_DIR\}/\.claude/hooks/(product|integrator|ecosystem|design|orchestrator)/` применяется к `args[0]`, а не к `command`. В обоих файлах это записано с 🛑-предупреждением: классификация по `command == "node"` смела бы **любой сторонний node-хук** в ecosystem-owned корзину и **удалила** его — прямое нарушение wipe-protection контракта.
- **Дедуп переехал с `command`-строки на пару `(command, args)`.** Дедуп по одному `command` схлопнул бы все хуки события в один.
- **Prune-классификатор узнаёт ОБЕ формы** — legacy shell (`^node\s+\.claude/hooks/…` и вариант с плейсхолдером) и текущую exec. Это и **есть миграционный механизм**: на ближайшем `/ecosystem:update` legacy-записи существующего проекта классифицируются как owned, отбрасываются и переизлучаются в exec-форме. Отдельный migration runner не нужен и не строился; дублей не возникает именно потому, что старая форма распознаётся классификатором, а не проваливается в «preserved verbatim».

Синхронно обновлены: JSON-примеры и лог-сводки в обоих файлах (+ новая строка сводки «Migrated to absolute form»), `_comment` в `settings.json.template`, три doc-comment'а регистрации в consumer-зоне (`drift-check.js`, `session-fabric-status.js`, `override-sweep-check.js`).

**Осознанно НЕ тронуто (родственный экземпляр того же класса, вне рамки этого фикса):** `dev/meta-improvement/scripts/install-dev-hooks.cjs` минтит команды dev-хуков **самого репо** тоже относительными (`node dev/meta-improvement/hooks/<file>`, плюс guard-форма `[ -f p ] && node p || true`). Это детерминированный генератор — чинится одной функцией `commandFor()`, но правка перезапишет `settings.local.json` владельца на ближайшем `npm install` и заслуживает отдельного решения. Bring-forward: при первом же наблюдении молчаливого падения dev-хука, либо вместе с любой следующей правкой `install-dev-hooks.cjs`.

### Outcome

`npm run verify` зелёный целиком (24 шага, exit 0) — как и на baseline до правок; `npm run smoke:hooks` — 47 хуков, 0 падений. Живой эффект проверяем только на пилоте после доставки: до `/ecosystem:update` хуки существующих проектов остаются сломанными ровно в тех сессиях, где cwd уходит из корня.

### Lessons

1. **Enforcement, который может молча умереть, обязан быть абсолютным и считаемым.** Носитель принуждения — это не только «правило имеет код», но и «код гарантированно стартует». Относительный путь × persistent cwd × non-blocking = отключение принуждения без единого следа; каждый множитель по отдельности выглядит безобидно.
2. **Правильная идея, не дотянутая до точки входа, не работает.** `CLAUDE_PROJECT_DIR || cwd` жил в телах пяти хуков и создавал ложное ощущение решённости — но тело не выполняется, если процесс не стартовал. Проверять надо границу запуска, а не внутренности.
3. **Несущую форму — верифицировать по документации, а не по приорам.** Форма из брифа (`node "$CLAUDE_PROJECT_DIR/..."`) выглядела очевидной и была бы принята «на глаз»; добор показал, что она ломается на Windows без Git Bash, а канон харнесса — другой (exec-форма с харнесс-подстановкой). Цена добора — минуты, цена ошибки — второй раунд молчаливых падений на другой платформе.
4. **Смена формы записи меняет и логику владения ею.** Переход на exec-форму обнулил дискриминирующую силу поля `command`; не заметив этого, «косметическая» правка формата вынесла бы сторонние хуки пользователя. Меняя представление — перечитывай всех, кто по этому представлению принимает решения.
