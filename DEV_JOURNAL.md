## DEC-DEV-0198 — Кампания «до-PROD»: pre-flight-аудит поверхности + Волна A (готовая поверхность перед стройкой Epic E)

**Context.** Владелец (2026-07-13): «делаем одним большим скоупом всё, что осталось до вывода экосистемы в прод как фабрики продуктовой разработки — с проверкой состояния проекта до старта, оркестрацией и делегированием так, чтобы исполнители сделали реально то, что ожидается, без потери сути». Кампания заведена как живой трекер `dev/plans/PROD_READINESS_CAMPAIGN.md`. Решения владельца по 6 открытым развилкам зафиксированы там же (§1); вопрос №3 делегирован мне.

**Pre-flight (7 агентов, workflow `prod-preflight`, 1.24 M токенов).** Разведка поверхности + синтез с адверсариальной сверкой отчётов между собой. Вскрыла **два переворачивающих факта**, которых не было ни в одном долговом доке:

1. **VM физически недоступна ПРЯМО СЕЙЧАС, и это не софт.** `SEAM.md` §4.5 (сегодняшним числом): ssh не поднимается не из-за sshd/NAT — гость не доходит до userland (`GuestAdditionsRunLevel=0`). Корень: VirtualBox на хосте исполняется по **Hyper-V/NEM-пути** (`HMR3Init: … VT-x is not available`), VBS+Credential Guard забрали аппаратную виртуализацию, гость ползёт на ¼ скорости и не успевает догрузить sshd. ⇒ порядок владельца «до прода → обновить пилот → прогоны → **потом** чинить VM» физически неисполним: обновление пилота и все смоук-прогоны VM-gated. Единственная правка порядка: **починка VM (операция владельца — Hyper-V/VBS+reboot) должна лечь ДО фазы прогонов, а не в конец.** Repo-сторона Epic E от VM не зависит — строится сейчас.

2. **Дефект нарезки kickoff'а Epic E — самый опасный риск кампании.** `EPIC_E_READINESS.md:52-61` ставит E.F (F3-wiring, «floor реально упирается в deploy») **после** E.B/E.C. Но floor в этом коде — **не ambient-guard, а чистая функция** (`autonomy-policy.cjs:179-192`): срабатывает ровно там, где позвали `resolve()`. При этом ни один state чартера не объявляет `operation_class`, а `env_tier` берётся из **глобального** `limits.json` и per-state объявлен быть не может (`fabric-engine.cjs:296-304`). ⇒ строитель E.B, честно исполнивший бриф, построит deploy, который **никогда не зовёт резолвер** — floor «непробиваем» на бумаге, но не участвует. **Тихий зелёный auto-deploy.** Резолюция: вызов `autonomy-policy resolve` (CLI-seam) + per-state `env_tier` подняты из E.F в **acceptance-критерии E.B/E.C**.

Плюс два новых дефекта bootstrap (в долгах их не было): use-after-free временной директории (`ECOSYSTEM_HEAD` безусловно затирается в `unknown`) и утечка всего дерева `tests/` в `.claude/` пилота через denylist-`cp`.

**Решение по вопросу №3 (делегировано владельцем): НЕ эскалировать `check-inventory-sync` до 🔒.** Оставить ⚙ (только в `npm run verify`). Три причины: (1) чекер сканирует весь репо — вешать на каждый `git commit` = платить сотни раз ради дефекта, который ловит следующий же `verify`; (2) `process-gate` — общий ресурс на пути каждого коммита и сам skip-not-abort (внутренняя ошибка → exit 0); (3) закрытый разрыв был «правило не принуждалось **ничем**» — между «ничем» и «verify падает» разница качественная, между «verify падает» и «коммит блокируется» — вкусовая.

**Решение по вопросу №2 (ветка dev-хуков) + переоценка DEF-CTX-4/6.** Ветку `fix/dev-env-delivery` бросаем (не удаляем — археология). Обоснование владельца: на VM — рабочий пилот со слоем экосистемы, а не dev-копия репо. Pre-flight подтвердил: слой едет в пилот **через git самого пилота** (304 файла в `.claude/` закоммичены), ни клона экосистемы, ни bootstrap, ни npm на целевой машине не нужно. ⇒ dev-хуки (DEF-CTX-4) и память (DEF-CTX-6) на VM не нужны — это инструменты **разработки** экосистемы. НО pre-flight нашёл цену, которую нельзя проглотить молча: `enable-d7-audit.md:68` вшивает в пилот хук с абсолютным путём в репо экосистемы ⇒ убрать репо с VM = убить D7-аудит VM-прогонов. Оставлено явной развилкой A12 (не молчаливым закрытием).

**Волна A — готовая поверхность (5 зон, каждая = строитель + адверсариальный проверяющий, opus).** Все 5 зон — PASS; проверяющие не пересказывали отчёты, а **перепрогоняли проверки сами** (M-1: живой `</script>`-пейлоад ломает непропатченную страницу, инертен в пропатченной; blind-law генератора каталога проверен двумя адверсариальными регрессиями; prune-семантика подтверждена по коду). Итог интегрирован полным `npm run verify` = **exit 0** (все 18 звеньев, включая 2 браузерных смоука, вернувшихся после `npm install`) + мой спот-чек двух рисковых диффов:

### Addendum — E.A построена (Волна B часть 1, owner-gated)

**E.A = Integrator оснащает deploy-capability** (суб-фаза Epic E1, дизайн-SSOT `EPIC_E_READINESS.md:52-53`). Построено трёхстадийным конвейером (дизайн→сборка→адверсариальная проверка, все opus), вердикт проверяющего PASS, полный `npm run verify` = exit 0.

Три артефакта (Integrator-сторона, §8.3): `skills/integrator/deployment-provisioning.md` (методология оснащения) · встроенный reference CNT-контракт deploy-capability · `agents/integrator/deployer.md` (role-агент).

**Ключевое решение — §8.3 закрыта структурно, а не политикой.** Граница «Integrator оснащает / Orchestrator исполняет» (SPEC:995-1008) обычно держится текстом («You DO NOT run deploy»). Строитель усилил её **лишением инструментов**: `deployer` несёт `tools: Read, Grep, Glob` — без `Bash`/`Write`/`Edit`. Агент физически не может вызвать `systemctl`/`ssh`/флип симлинка **даже при неверном брифе**. Сиблинги (`contract-designer`, `tool-profiler`) `Bash` несут — значит withhold намеренный, не копипаст. Это сильнейшая форма enforcement'а из доступных: не «агенту сказано не делать», а «агент не может». Плюс машинная запись раскола — CNT `producer: deployer` / `consumer: deploy-to-stage`.

**Минорная находка проверяющего закрыта оркестратором:** CNT-шаблон вводил поле `contract_schema_version`, которого нет в SPEC §5.1, при том что скилл декларирует «maps §5.1 exactly» — ровно класс «AI добавил поле для естественности» (инвариант DEC-DEV-0012). Строка убрана; расширение схемы, если понадобится, — через явное решение, не тихую вставку.

**Owner-gate (решение владельца №1) — открытые вопросы к предъявлению перед E.B:** (a) канал-триггер деплойера (`/integrator:provision <cap>` рекоменд. vs inline-spawn vs `/integrator:add --capability`) — дизайн команду намеренно не поставил; (b) подтвердить, что CNT едет как `draft`; (c) генеральность имени скилла; (d) prisma-absent: note-and-proceed vs hard-block. VM-gated (не дефекты): флип CNT `draft→active` (нужен живой verify = E.D), pilot-side регистрация в `active-tools.yaml`/`pmo-mapping.yaml`, байт-точная сверка формы CNT с реальным инстансом пилота.

**Acceptance для E.B (передано контрактом, НЕ scope E.A):** `deploy-to-stage.mjs` обязан (1) нормализовать CRLF при парсинге манифеста; (2) звать `autonomy-policy resolve` + объявлять per-state `env_tier` — против «тихого зелёного auto-deploy» (кампания §3.2).

### Addendum — Фундамент E1: B4 (F3-core) + /integrator:provision (owner-gate пройден)

**Owner-gate после E.A пройден** (решение владельца 2026-07-13): канал-триггер деплойера = `/integrator:provision` (новая команда); строить весь repo-side сейчас (unvalidated до восстановления VM); prisma-absent = note-and-proceed; CNT = draft.

**B4 = F3-core** — резолвер, на который обопрётся E.B (построен ПЕРЕД процессами намеренно: §3.2 кампании — floor раньше deploy; иначе E.B дал бы тихий auto-deploy мимо резолвера). Дизайн→сборка→адверс-проверка, вердикт PASS, verify exit 0.

**Ключевое дизайн-решение — семантика L3 как одноячеечная дельта.** F2 держал L3 затычкой (`effLevel='L2'`). Снятие затычки могло раздуться в переписывание матрицы. Дизайнер свёл F3 к **одной ячейке**: `L3 × staging` для не-floor операций → `auto` (вместо `consilium-gate`). Обоснование — оси ортогональны: `env_tier` = ось радиуса поражения, floor = ось необратимости; лестница L0→L3 растёт по доверию к автоматике на НЕ-floor операциях, floor неизменен. L3 приземляется там, где радиус ограничен (staging: обратимый симлинк-своп, dev-tier секреты, сетка healthcheck→auto-rollback), и НЕ на prod (floor + консервативный consilium). Модель безопасности сдвигается «обдумать-до-действия» (L2 жюри до деплоя) → «обнаружить-и-откатить» (L3 деплоит, полагаясь на пост-деплой сетку) — это БОЛЬШЕ автономии, не безрассудство; оператор явно выбрал `profile: autonomous`.

**Floor непробиваем на L3 — доказано по построению, не по тесту.** Floor-проверка — early-return ПЕРВОЙ (`autonomy-policy.cjs:191-198`), выше и rollback-ветки, и матрицы. Все правки F3 строго ниже. ⇒ floor-класс никогда не достигает нового кода. Закреплено свипом floor×{L0..L3}×{dev,staging,prod} + тестом монотонности автономии L0≤L1≤L2≤L3.

**operation-класс `rollback` — level-INDEPENDENT (важно).** rollback ∉ floor. Правило: staging→`auto` на ЛЮБОМ уровне (включая дефолтные L0/L1), prod→`human-gate` всегда. Почему level-independent: D-4/D-9 auto-rollback брекет (`deploy_failed → auto-rollback → rolled_back`) обязан срабатывать без человека на РЕАЛЬНОМ уровне проекта (L1 дефолт). Если бы rollback ехал по generic-матрице, на L1 он был бы `human-gate` — auto-rollback молча сломан, а выглядит зелёным. Правило сидит ВЫШЕ матрицы (зеркало floor, обратное направление). Safe-by-construction: rollback двигает систему только к ранее-задеплоенному known-good.

**per-state env_tier** — `resolveDisposition` (fabric-engine:301) получил префикс `meta.env_tier ||` перед глобальным `env.limits.env_tier`; отсутствует ⇒ байт-идентично прежнему (backward-compat). Нужно, т.к. глобальный limits не различит deploy-состояние от build-состояния в одной линии.

**Контракт для E.B (передан в бриф):** deploy-состояния чартера ОБЯЗАНЫ объявить `operation_class:'deploy_staging'|'rollback'|'prod_deploy'` + `env_tier` в `meta`, и ОПУСТИТЬ `meta.autonomy` (иначе `prescribe` флорит в human-gate, убивая staging-автономию). Резолвер инертен, пока чартер не объявит meta. `rollback` в meta должен быть ТОЧНО `'rollback'` — иначе едет в generic-колонку → human-gate на дефолте → auto-rollback молча выключен.

**Мелочь для E.B:** `run.md` несёт stale-прозу про «L2/L3 → consilium» (2 региона: ~:294-296 + скобка ~:350-351) — теперь неточно для L3×staging=auto. Не load-bearing (актуатор кейается на `disposition`, не на level), но поправить при регистрации E.B.

### Addendum — E.B/E.C (deploy-брекет) + E.E (healthcheck-звено): repo-сторона Epic E завершена

Логика fuzzy-матчинга НЕ тронута — цель была сделать промах громким, а не сломать то, что работает.

**Lessons.**
24. **Live-прогон ловит то, что фикстуры не могут поймать by construction.** FIND-3 — контрактный дефект (два каталога, два ключа), который **маскировался случайным совпадением имён** в 5 случаях из 6. Вывод не «пишите больше юнитов», а «прогоняйте на субстрате, который вы не сочиняли».

26. **Консервативный дефолт + потерянная причина = невыводимый блок.** `unknown → DEGRADED` безопасно и правильно. Но если причина не доезжает до `run.json`, пользователь видит только «деплой опять просит человека» и не может связать это с отсутствующим `pg_isready`. 27. **Не мутируй субстрат, пока по нему идёт чтение (мой промах).** Запустив аналитика на read-only разбор DEGRADED, я параллельно доустановил клиенты БД на VM. Аналитик увидел мир уже после мутации и **ошибочно атрибутировал** дефект «искажению LLM-релея, причина не установлена». Диагноз был бы ложным, если бы я не держал в руках собственный замер «до». Правило read-only-окна — не бюрократия.
28. **Не тиражируй сводку исполнителя, не пересчитав (рецидив-профилактика D13).** Строитель отчитался, что `--feature FM-006` даёт `BLOCKED_ON_CAPABILITY` — «реальный boot-blocker, который скрывал слаг». Но это было на **его фикстуре**; живой пилот на том же ключе даёт `requests: []`. Утверждение не попало ни в CHANGELOG, ни сюда — проверка на реальном пилоте назначена отдельным шагом.

## DEC-DEV-0200 — Run-ledger терял исход прогона: `p7_result` ≠ `result`, и упавший бут месяцами писался в трейс как `null`

**Context.** Живой P7 на VM-пилоте (2026-07-14) реально **упал**: бэкенд не поднялся (NestJS DI-ошибка), процесс честно вернул `p7_result: "FAILS_TO_START"`. В трейсе прогона (`runs/…-kj2v2w/run.json`) осталось:

```json
"result_summary": { "verdict": "READY_TO_SMOKE", "result": null, "readiness": "READY", … }
```

`result: null` — **прогон с упавшим бутом из леджера неотличим от зелёного.** `verdict: READY_TO_SMOKE` — это вердикт *готовности к смоуку*, не исход смоука; читатель леджера видит слово «READY» и идёт дальше. Это не косметика: компонент 2 гейта `dev/gates/SUBSTRATE_GRADUATION_GATE.md` («трейсы каждого прогона») — единственный незакрытый компонент prod-порога, и опирается он ровно на run-ledger. Леджер, который пишет `null` вместо `FAILS_TO_START`, **не является трейсом**: он молча зеленит провал.

**Корень — ключи не совпадают, и никто их не сверял.** `summarizeResult()` читал `r.result`. Что процессы отдают на самом деле (сверено по исходникам, не по памяти):

| Процесс | ключ исхода | readiness | до фикса в леджере |
|---|---|---|---|
| P6 `validate-feature-impl` | `result` (+ `go_gate` алиас) | `readiness` + `readiness_reasons` | ✅ читался |
| E.B `deploy-to-stage` | `result` | `readiness` + `readiness_reasons` | ✅ читался |
| E.C `rollback-release` | `result` | `readiness` (reasons **нет**) | ✅ читался |
| **P7 `runtime-smoke-readiness`** | **`p7_result`** | `readiness` + `readiness_reasons` | 🔴 **терялся → `null`** |
| **P5 `feature-to-tdd-impl`** | **`go_gate`** (top-level `result` **отсутствует**) | `readiness` | 🔴 **терялся → `null`** |
| P2 / P3 / P4 | скалярного исхода нет вовсе | — | `null` — и это **корректно** |

**Вторая потеря, которой бриф не знал: P5.** У `feature-to-tdd-impl` нет ключа `result` в принципе — его GO-гейт лежит в `go_gate`. Значит `summarizeResult` отдавал `{verdict: null, result: null}` на **каждом** P5-прогоне. Следствие в consumer-zone: `hooks/product/lib/impl-evidence.cjs::collectRunsEvidence` по собственному докстрингу ищет «the LATEST gate verdict across **P5**/P6-class gate runs», а гейтит по `GATE_VERDICTS.has(rs.result || rs.verdict)` — то есть **не мог увидеть ни одного P5-прогона никогда**. Докстринг обещал то, чего код не делал.

**Третий разрыв — обещание PR #190 не исполнялось.** Мы добавили `readiness_reasons` в результаты P7 и `deploy-to-stage` с комментарием в коде: *«the gate must be auditable from run.json alone»*. `summarizeResult` это поле не переносил ⇒ в `run.json` его не было ⇒ обещание было ложным ровно на следующем слое. Плюс форма результата бывает **обёрнутой** (в старой ledger-строке `readiness: null` при вложенном `verdict.readiness: "DEGRADED"`) — суммаризатор жёстко ждал одну форму и читал `null` поверх живых данных.

**Фикс — расширено ЧТЕНИЕ, а не переименована схема** (инвариант DEC-DEV-0012: не «улучшай» схему, которую только потребляешь; ни одного нового имени поля в процессах не заведено).
- `OUTCOME_KEYS = ['result', 'p7_result', 'go_gate']` — контракт ключей исхода, это **собственные имена процессов**, в порядке приоритета. Плюс разбор вложенной формы (`verdict.<key>`), закрывающий обёрнутый конверт: оттуда теперь достаются и исход, и `readiness`.
- `readiness_reasons` переносятся в `result_summary` и в ndjson-строку (обещание PR #190 стало правдой). Отсутствуют ⇒ `null`, а не фейковый `[]` — честно показывает, что E.C `rollback-release` причину readiness **не раскрывает вовсе** (следующая правка, здесь не трогал: это правка процесса, а не леджера).
- Backward-compat: пять исходных ключей `result_summary` сохранили имя, позицию и смысл (`impl-evidence.cjs` читает `verdict`/`result`/`readiness` именно оттуда). Формы P6/E.B/E.C суммируются байт-в-байт как раньше — покрыто тестом.
- **Дисклоз (решение, а не косметика).** `null` раньше означал две несовместимые вещи: «процесс не дал исхода» (P4 — норма) и «дал, а мы не прочитали» (P7 — дефект). Одно значение на два смысла ⇒ дефект неотличим от нормы, что и обеспечило ему выживание. Разведено: `outcome_key` — провенанс (из какого ключа взят исход; `null` ⇒ процесс исхода не давал), и `unread_outcome_keys` — **алярм**: ключи вида `*_result`/`*_gate`/`*_verdict`, которые леджер видит, но читать не умеет. В ndjson-строку алярм попадает **только когда не пуст** (тихо в норме, громко в аварии). Существуй этот дисклоз с первого дня — `['p7_result']` торчал бы в первом же `run.json`, и дефект не прожил бы и одного прогона.

**Гейт против класса, а не против симптома.** Добавлен тест-сверка (`tests/orchestrator/run-ledger.test.cjs`), который читает **реальные исходники** `orchestrator/processes/*.mjs`, вытаскивает depth-1 ключи всех `return {…}`-блоков и падает, если процесс отдаёт outcome-образный ключ, которого леджер не читает. Парсер — два независимых прохода (brace-walk ∪ line-anchored regex), объединение: промах здесь означал бы слепоту гейта, а over-report — всего лишь лишний крик. При нуле распарсенных блоков тест падает громко («guard went BLIND, fix the parser») — «не вижу» не имеет права читаться как «ничего нет».

**Адверсариальная проверка (гейт зелёный сам по себе не доказывает ничего).** Две мутации против реального дерева: (1) откат `OUTCOME_KEYS` к до-фиксному `['result']` → гейт **краснеет** и называет `p7_result` + `go_gate` — то есть ловит именно исторический дефект; (2) переименование в живом исходнике P7 `p7_result` → `p9_result` → гейт **краснеет**, называет файл, ключ и что делать. Обе восстановлены; `npm run verify` = exit 0.

**Lessons.**
29. **Суммаризатор, чью входную форму никто не сверял с источником, — молчаливый лжец.** Леджер читал `result`; процессы говорили `p7_result` и `go_gate`. Никто никогда не сверял два списка — а юниты леджера гоняли **выдуманную** форму (в фикстуре стоял `counts`, которого нет ни в одном из 8 процессов). Тест, форму для которого автор кода придумал из головы, подтверждает код, а не реальность: он был зелёным ровно всё то время, пока леджер терял исходы. Отсюда единственный работающий класс защиты — **сверка с живым источником** (парсим исходники процессов), а не с фикстурой, которую мы же и сочинили. Ср. урок 24: та же болезнь, другой слой.
30. **Одно значение на два смысла — гарантия, что дефект неотличим от нормы.** `null` = и «исхода не было» (законно), и «исход был, а мы промахнулись ключом» (авария). Пока эти два состояния делят одно представление, никакой мониторинг их не разделит — не потому что плохо смотрели, а потому что смотреть не на что. Дефолт обязан быть **говорящим**: провенанс (откуда взято) + алярм (что видел, но не смог прочесть).
31. **Гейт, объявленный в комментарии, гейтом не является.** PR #190 написал в коде «the gate must be auditable from run.json alone» — и тут же терял `readiness_reasons` на следующем слое, так что в `run.json` их не было. Обещание, данное в комментарии, не исполняется само собой; исполняется только то, что кто-то проверил **сквозь все слои** до артефакта, на который ссылается обещание.

## DEC-DEV-0201 — Первый деплой был невозможен в принципе: `draft` смешан с readiness (архитектурный дедлок в стыке E.A↔E.B)

```json
{"result":"BLOCKED","readiness":"ENV_NOT_READY","flipped":false,"disposition":null,
 "readiness_reasons":["deploy-manifest for \"deploy-staging\" not deployable (present=false, status=draft-only) … → ENV_NOT_READY; provision it via /integrator:provision deploy-staging"]}
```

| **readiness** | **МОЖЕМ ли вообще?** субстрат поднят? оснастка есть и исполнима? | **`block`** (`ENV_NOT_READY`) |
| **contract (доверие)** | **КТО решает?** верифицировал ли хоть один живой прогон этот контракт? | **`human-gate`** |

`deploy-to-stage.mjs:214` (`manifestOk = present && status !== 'draft'`) и промпт парсера `:211` («status is draft-only → `present:false`») отвечали на **второй** вопрос **ответом на первый**. Результат — замкнутый круг:

```
E.A ОБЯЗАН отдать CNT `draft`      (собственное правило: не объявляй `active` до живой верификации)
E.B ОТКАЗЫВАЛСЯ деплоить не-`active` (present=false → ENV_NOT_READY → BLOCKED)
живая верификация возможна ТОЛЬКО через успешный деплой
⇒ ПЕРВЫЙ ДЕПЛОЙ НЕВОЗМОЖЕН В ПРИНЦИПЕ
```

**Отсутствующая capability — это block. Отсутствующий человек — это gate.** Блок на оси доверия недостижим **по построению**: единственное, что могло бы его снять (живой прогон), он же и запрещает. Такой блок — не строгость, а логическая ошибка.

**`disposition: null` — второй, более тихий симптом.** Резолвер §3.2 **даже не вызывался**: префлайт закоротил раньше. То есть вся мутирующая ветка гейта (сердце E.B, ради которого он строился) на живом субстрате **ни разу не исполнялась** и оставалась непротестированной. Дедлок маскировал ещё и это.

**Инверсия, которую вскрыла проверка (важнее самого фикса).** Прогнав до-фиксный резолвер руками:

```
$ node autonomy-policy.cjs resolve --operation-class deploy_staging --risk HIGH \
      --env-tier staging --readiness READY --override L3
{"disposition": "auto", ...}
```

То есть **сними ложный блок наивно — и L3×staging отдал бы молчаливый auto-деплой по контракту, который никто никогда не верифицировал.** Ложный `ENV_NOT_READY` случайно делал работу гейта — плохо, не на своей оси, ценой дедлока, но делал. Поэтому фикс — **не** «убрать блок», а **развести оси**: убрать блок И поставить на освободившееся место настоящий гейт. Убрать блок в одиночку было бы регрессией безопасности, замаскированной под багфикс.

**Фикс.**
1. **`deploy-to-stage.mjs` — оси разведены.** `present` = **факт** (файл есть + парсится + несёт исполнимый step-list; `status` в выражении `manifestOk` **не участвует вовсе**) → `!present` ⇒ `ENV_NOT_READY`, как и раньше. `status: draft` = **доверие** → readiness **не понижается**, признак едет в резолвер + объяснение в `readiness_reasons` (объяснение, не блок).
2. **`autonomy-policy.cjs` — `applyContractGuard`,** зеркальный `applyReadinessGuard`: `draft` понижает `auto → human-gate` (**не** `block`); `consilium-gate`/`human-gate`/`block` не трогает (downgrade-only); `--accept-draft-contract` = **явный акт владельца** (без него `auto` по draft не бывает). **Floor неприкосновенен**: guard стоит НИЖЕ floor-early-return и **никогда не повышает** диспозицию — `prod_deploy` × L3 × `draft` × `--accept-draft-contract` = `human-gate` + `floor_hit: true` (проверено свипом по всем уровням × средам). Отсутствие `--contract-status` ⇒ поведение **байт-в-байт** прежнее (доказано diff'ом против до-фиксного HEAD: пусто) — P5/P6/fabric не затронуты.
3. **Цикл замкнут:** на `DEPLOYED` процесс возвращает `contract_evidence` (CNT id + `run_id` + `verdict: live-verified`) + дисклоз «CNT может быть флипнут в `active`». **🔒 §8.3 соблюдён:** Orchestrator **сообщает**, но **не пишет** в `.claude/integrator/**` — флип контракта остаётся прерогативой Интегратора. Замкнуть цикл, нарушив §8.3, было бы обменом границы зон на удобство.

**Почему repo-side этого не поймал (главный вопрос).** Обе стороны стыка по отдельности **корректны, осмысленны и юнит-покрыты**:
- E.A: «не объявляй контракт `active`, пока живой прогон его не верифицировал» — **правильное** правило (иначе контракт врёт);
- E.B: «не деплой неоснащённую capability» — тоже **правильное** правило (иначе деплой фабрикует step-list).

Дефект живёт **не в компоненте, а в стыке двух правильных правил** — и виден только на **первом реальном деплое**. Тесты гоняли ячейки `present:false` и `present:true/active`; ячейку **`present:true` × `draft`** никто не спросил — именно потому, что обе стороны «очевидно правы», и никто не пересёк их в одной таблице. Юниты обеих сторон были зелёными всё это время, `verify` = exit 0.

**Гейт против класса.** Тесты пишутся так, чтобы падать на **реальном** выражении, а не на его пересказе: `manifestOk` **извлекается из исходника и исполняется** (`new Function`) против фикстур, резолвер-команда **собирается** из живого шаблона. Адверсариальная проверка: (1) вернул `status !== 'draft'` в `manifestOk` → дедлок-тест **краснеет**; (2) переписал guard так, чтобы `acceptDraft` **повышал** диспозицию (правдоподобная ошибка реализации) → краснеют **5** тестов, включая floor-инвариант и CLI-floor. Обе мутации откачены; `npm run verify` = exit 0.

**Lessons.**
32. **Если компонент A ОБЯЗАН произвести артефакт в состоянии X, а компонент B ОТКАЗЫВАЕТСЯ работать с состоянием X — это дедлок, даже если оба правила выглядят безупречно.** Проверка, которую можно провести на бумаге до всякого прогона: «кто может вывести систему из X, если вход в X обязателен?» Нет ответа ⇒ круг замкнут. Ищите такие пары в стыках, а не в компонентах: компонентные тесты их не видят **никогда** — каждая сторона проходит свои юниты.
33. **Смешение осей «можем ли» и «кто решает» — не педантизм, а источник неисполнимых состояний.** Отсутствие *возможности* и отсутствие *санкции* требуют противоположных реакций: первое — блок (ждать среду), второе — гейт (спросить человека). Схлопнешь их в один флаг — получишь либо дедлок (как здесь), либо, при наивном исправлении, тихий auto по непроверенному контракту. **Отсутствующая capability — блок; отсутствующий человек — гейт.**
34. **Ложный блок может годами делать работу отсутствующего гейта — и «починка» блока эту работу молча снесёт.** Здесь `ENV_NOT_READY` случайно закрывал дыру, которой не было гейта: убери его в одиночку — и L3 отдал бы auto-деплой по неверифицированному контракту. Прежде чем снимать ограничение, спроси: **что оно на самом деле держало?** Иногда ответ — «то, чего мы ещё не построили».

## DEC-DEV-0203 — E.A написал рецепт, кухню не построил никто: сцена деплоя не материализовалась, юниты прибиты к релизу, парсер-гейт стоял на LLM

**Context.** Второй живой прогон deploy-контура (E.B, 2026-07-14) — уже после снятия дедлока 0201. Три дефекта, все **только на реальном субстрате**: repo-side `verify` = exit 0, юниты зелёные, процесс структурно безупречен.

### FIND-B (блокер) — сцены не существует

`deploy-manifest.yaml` (авторит E.A) объявляет `deploy_root: "~/deploy/my-first-test"`, layout `releases/{{TIMESTAMP}}` + симлинк `current` + `shared/{.env, logs/, uploads/}`, 4 шага и 3 systemd-юнит-шаблона. **Ничто из этого не материализуется.** В `deploy-to-stage.mjs` не было ни одного вхождения `deploy_root` / `homedir` / `expand` — `~` никогда не разворачивался, `~/deploy/` не создавался, `releases/<ts>` не выкладывался, `shared/.env` (откуда `migrate` берёт `DATABASE_URL`) не создавался, юниты в systemd не ставились.

**Первый деплой был невозможен в принципе — ровно та же форма, что и дедлок 0201: две правильные половины и пропасть между ними.** Интегратор *описывает* сцену, но кто её *строит*, не было сказано **нигде** — ни в скилле, ни в процессе, ни в CNT. Обязанность без адресата = обязанность, которую не исполняет никто.

### FIND-B, вторая половина — юнит, глухой к флипу (нашлась при проверке гипотезы)

Шаблоны параметризованы **`{{RELEASE_DIR}}`** — *конкретным* `releases/<ts>`. Юнит, прибитый к одному релизу, **глух к флипу**: `current` переезжает, юнит — нет, `systemctl restart` поднимает **старый** релиз. И тогда healthcheck **проходит** — старый код жив, здоров, слушает тот же порт.

**Прогон вернул бы `DEPLOYED`, не задеплоив ничего.** А эта ложная зелень — ровно тот `contract_evidence`, который флипает неверифицированный `draft`-CNT в `active`: **сломанная capability сертифицировала бы сама себя**. Тем же молчанием ломался и E.C-rollback (флип обратно тоже ни на что не влияет).

Контракт Capistrano — одна строка: **юнит смотрит на `current`; флип и есть деплой.** `{{RELEASE_DIR}}` законен в шаге `build` манифеста (сборка принадлежит одному релизу) и **не имеет права появляться в юните**.

### FIND-A (high) — readiness-гейт стоял на стохастическом парсинге

`present` / `status` / `steps` брались у **sonnet-субагента**. Один и тот же неизменённый файл (mtime старше всех прогонов) распарсен по-разному: полный 4-шаговый список → READY, через 18 минут `step-list=MISSING` → ENV_NOT_READY; один раз агент вернул самопротиворечивую пару `present:true` + `steps:[]`. Ирония: промпт агента **сам цитировал** детерминированный `capability-probe.cjs::extractManifest` — и всё равно парсил LLM-ом.

### FIND-D (medium) — у упавшего деплоя след беднее, чем у заблокированного

`run.json` с `DEPLOY_FAILED` нёс только `result`/`readiness`. `disposition: auto` — факт, что гейт §3.2 **санкционировал мутацию** — пришлось доставать из транскрипта.

**Корень оказался НЕ там, куда указывал симптом.** Return-арки процесса несли `disposition`/`flipped`/`release`/`healthcheck` **всё это время**. Их выбрасывал **леджер**: `run-ledger.cjs::summarizeResult` проецировал возврат на фиксированный набор из 8 ключей. Починить только арки — значит не починить ничего, что доезжает до `run.json`.

**Decision.**

1. **Scene-bootstrap** — новая мутирующая стадия в фазе `Deploy` (`label: 'scene-bootstrap'`, opus): разворачивает `deploy_root`, `mkdir -p` сцены, сеет `shared/.env` из корня проекта (staging v1 = dev-tier секреты, A-1..A-9), выкладывает `releases/<ts>`, симлинкует `shared` внутрь релиза, материализует systemd-юниты (+ `daemon-reload` / `enable`). Идемпотентна. **Строго ПОСЛЕ гейта §3.2** — она создаёт каталоги, пишет файл секретов и ставит юниты, т.е. это мутация; в префлайте она обошла бы floor.
2. **`orchestrator/lib/deploy-manifest.cjs`** — детерминированное чтение манифеста через CLI-шов + агент-транспорт (та же форма, что у `autonomy-policy.cjs`). Парсер YAML-подмножества на голом Node (либа копируется в пилот, где нет `node_modules`), CRLF-толерантный, **без часов** (timestamp приходит аргументом — иначе N прогонов не были бы байт-идентичны).
3. **Гейт оснастки** — либа читает каждый `.service.template` и, если юнит прибит к релизу, отдаёт `blocking_defects: ['unit-template-release-pinned']` → `deploy-to-stage` даёт `ENV_NOT_READY` («capability мис-оснащена») → `BLOCKED`, `flipped: false`, лекарство = `/integrator:provision`. **Чиним оснастку, а не обходим её:** скилл `deployment-provisioning.md` §1 переведён на `{{CURRENT_LINK}}`; Оркестратор шаблон Интегратора **не переписывает** (§8.3).
4. **Единый аудит-след** — все result-несущие return-арки несут один и тот же набор ключей (+ `failure_class` поднят на верхний уровень); wiring-тест это принуждает. И `summarizeResult` получил `decision_trail` (кто санкционировал / что переехало / что сломалось / что раскрыто) — **иначе богатые арки не доехали бы до `run.json`**.

**Ключевое дизайн-решение — что кладём в релиз.** Копируем **дерево исходников** (workspace-манифесты + `apps/**` + `packages/**` + конфиги), исключая `.git`, `.claude*`, `node_modules`, `dist`/`.next`/`build`, `.env`; затем **`pnpm install --frozen-lockfile` ВНУТРИ релиза**. Почему так:

- шаг `build` манифеста исполняется с `working_directory: {{RELEASE_DIR}}` ⇒ релизу нужны исходники и workspace-манифесты;
- **откат = флип симлинка назад ⇒ релиз обязан быть самодостаточным.** Отсюда **`node_modules` — пер-релизные, не общие и не симлинк**: общий `node_modules` дал бы новому деплою тихо переподвязать зависимости *старого* релиза, и «известно-хороший» релиз, на который мы откатываемся, поднялся бы на зависимостях, которых никогда не видел. Это не гипотетика — это то, что превращает rollback в ложь;
- пер-релизные зависимости дёшевы **именно потому, что это pnpm**: он хардлинкает из content-addressable store — диск ≈ 0, установка быстрая на тёплом сторе;
- `.env` — **симлинк** на `shared/.env`, не копия (иначе правка общих секретов не доезжает до релиза).

Отвергнуто: `git archive HEAD` (деплоит только закоммиченное, молча теряет untracked; привязывает деплой к чистому checkout'у) · копирование `node_modules` с хоста (тащит чужую арку нативных модулей).

**Проверка (empirics).** Парсер: 30 CLI-прогонов на реальной форме манифеста → **1 хеш** (тот же тест зашит в юниты, N=20). Идемпотентность: рецепт scene-bootstrap исполнен дважды на реальном дереве — второй прогон **добавил только новый релиз** (каталоги сцены переиспользованы, `shared/.env` не перезаписан, прошлый релиз цел и самодостаточен), исключения соблюдены, юнит материализовался на `current/apps/api`. `verify` = exit 0. **VM-gated остаются** (хост: Hyper-V/VBS off, WSL2 не стартует): POSIX-симлинки и атомарность `mv -T`, `systemctl daemon-reload/enable/restart` под sudo, `pnpm install` в релизе, живой healthcheck.

**Lessons.**

35. **«Кто это построит?» — вопрос, который надо задавать КАЖДОМУ объявленному артефакту.** Манифест объявлял `deploy_root`, layout и юниты; скилл добросовестно их авторил; процесс добросовестно их исполнял. Обязанность *создать* сцену не была записана **нигде** — и потому её не исполнял никто. Форма та же, что у 0201: две безупречные половины и пропасть. Тест на бумаге: **для каждого объявленного артефакта назови компонент, который его материализует.** Не называется — это и есть пропасть.
36. **Самый опасный дефект — тот, что падает ЗЕЛЁНЫМ.** Юнит, прибитый к релизу, не ронял деплой — он его *имитировал*: флип проходил, restart проходил, healthcheck проходил (старый код жив на том же порту), прогон рапортовал `DEPLOYED`, попутно выписывая непроверенному контракту фальшивую live-верификацию. **Ложная зелень дороже любого блока.** Если успех подтверждается пробой, которую **старое состояние тоже проходит**, — проба не доказывает ничего.
37. **Детерминированный факт обязан извлекаться детерминированно — тем более если на нём стоит гейт.** «Есть ли в файле step-list» — факт о байтах. Отданный LLM, он стал монетой, и монета падала в обе стороны: ложно-отрицательная блокировала годный деплой, ложно-положительная провела бы искалеченный манифест в реальную мутацию. Промпт **цитировал** детерминированный парсер — и всё равно парсил сам. Правило то же, что у резолвера §3.2: **диспозиция — код; агент только транспорт.**
38. **Симптом указывает на арку — дефект сидит в проекции.** FIND-D выглядел как «процесс не отдаёт полей»; процесс отдавал их всегда, их выбрасывал `summarizeResult`. Сводка, молча сужающая запись, **неотличима от процесса, который её не произвёл**. Чинить надо там, где теряется, а не там, где заметили. И это второй раз подряд в том же файле: DEC-DEV-0200 расширил его ради `readiness_reasons` и остановился на шаг раньше — **расширяя проекцию, спроси, что ещё она роняет.**

Оба warn-only; регистрация локальная (унаследованная дыра доставки dev-хуков — DEF-CTX-4, не чинилась).
4. **Инстанс #2:** `dev/semantic-continuity/SEAM.md` — шов сессии этой самой работы (валидируем протокол на себе).

**Отвергнутые альтернативы:** (a) полный вариант B сразу (секция в CLAUDE.md + D7-чеклист) — кодификация до валидации R10 = ритуал вместо механизма, ровно от этого предостерегал 0196; (b) немедленный глобальный уровень (N2→MDP) — радиус 47 проектов без валидации, T2; (c) блокирующие гейты швов — precision хуков не измерена, «строгий гейт с ложняками хуже отсутствующего»; (d) строить statusline→файл→хук мост для порога % — OQ-CS-02 показал возможность, но спроса нет, порог остаётся поведенческим+симптомным.

**Следующий шаг трека:** валидация R10 на живой передаче (сессия стартует только со шва, ACK фиксируется, потери грейдит не-автор-судья с fallback квоты) → инстанс #3 → решения владельца: N2 в глобальный MDP, промоушен в D7-паттерн. Очередь после (подтверждена владельцем): D13 per-сценарный пересуд → Informed Fetch → DEF-CTX-1..6.

### Lessons

39. **Знание правила в контексте ≠ его исполнение — передавай структуру принуждения, а не пересказ.** S2 сформулировала для преемника все правила, которые нарушила сама. Шов/бриф, который «рассказывает как надо», даёт те же 60–68%, что любая проза; работают ACK-чеклист, явные мандаты, гейты. Симметрично для агентских брифов: контракт + anti-patterns + обязанность вернуть расхождения.
40. **Шов, несущий только статус, теряет самое дорогое — инварианты, запреты среды и режим работы.** Кейс entry-63: ограничение «только на VM» жило в диалоге и умерло на границе сессий, после чего S2 ратифицировала самореферентную мутацию. В шаблоне v2 у этих трёх вещей теперь свои обязательные секции, и стоп-блок ре-инжектится хуком после компактации (push бьёт pull).
41. **«Изучи весь релевантный материал» — неоперационализируемая инструкция; критерий достаточности обязан быть satisficing-чеклистом с проверкой усвоения.** Строгий критерий полноты добора доказуемо невычислим (VoI NP^PP; ценность контрфактуальна — узнаётся абляцией), поэтому единственная честная форма — «прочти вот это, затем ответь на вот эти вопросы, потом правь». S2 прочла 5–7% корпуса и объявила себя готовой — ACK бы это поймал за минуту.

## DEC-DEV-0205 — E.A оснастил деплой, который не мог ни собраться, ни запуститься: codegen не был ничьим шагом, а юнит держал bare-команду

**Context.** Третий живой прогон deploy-контура (run `kxe0ls`, 2026-07-14) — первый, дошедший до build внутри свежесозданного релиза: префлайт прошёл целиком (флаки BR-079 пилота устранён правкой теста, коммит пилота `aa7a049`), §3.2-резолвер впервые вызван на живом пути (`disposition: auto`, L3, draft санкционирован `--accept-draft-contract`, `floor_hit: false`), scene-bootstrap 0203 впервые исполнен и отработал корректно (сцена из 13 объектов, пер-релизный `node_modules` за 7.3 с с тёплого стора, `.env` симлинк на shared, юниты на `current`). Упал на следующей никогда не исполнявшейся стадии — build внутри чистого релиза. Два дефекта оснастки, которую авторит deployer по `skills/integrator/deployment-provisioning.md`; оба невидимы repo-side (`verify` = exit 0, юниты зелёные).

### FIND-C1 (блокер) — манифест предписывает migrate, но Prisma-клиент не генерит никто

Релиз собирается в ЧИСТЫЙ пер-релизный `node_modules` (`pnpm install --frozen-lockfile` внутри `releases/<ts>` — решение 0203 о самодостаточности отката) ⇒ сгенерённого Prisma-клиента там нет никогда ⇒ `pnpm -r build` падает детерминированно: `packages/db: TS2305 — Module '"@prisma/client"' has no exported member 'PrismaClient'`. Dev-чекаут пилота маскировал это месяцами — клиент был сгенерён исторически. Тот же класс, что FIND-B 0203 (урок 35): манифест предписывает migrate (prisma опознана present), а codegen не предписан **никому**. Обязанность без адресата = обязанность, которую не исполняет никто.

### FIND-C2 — юнит с bare-командой умирает на exec, не отдав ни одного запроса

`mft-web.service` шаблон нёс `ExecStart=pnpm --filter @app/web start`. systemd не резолвит команды по PATH юзер-шелла (fixed compile-time search path; nvm / corepack / `~/.local/share/pnpm` для него не существуют) — юнит падает `status=203/EXEC`. Эталон корректной формы всё время стоял рядом: api-шаблон `ExecStart={{NODE_BIN}} dist/main.js`.

**Decision.** (форма 0203: чиним оснастку + ставим гейт против класса; юниты на РЕАЛЬНОЙ форме)

1. **Скилл:** codegen — шаг манифеста (`pnpm --filter @app/db exec prisma generate`, `working_directory: {{RELEASE_DIR}}`), **первый** в step-list (install уже сделан scene-bootstrap'ом, build впереди); тот же runtime-признак, что у migrate (schema present) — один флаг, два шага. Migrate обязан держать литерал `prisma` видимым (не прятать за opaque-скрипт `db:migrate:deploy`) — иначе гейт-потребитель слеп. §1: ExecStart-семейство — только абсолютные пути или плейсхолдеры; web-шаблон переведён на `{{NODE_BIN}} .next/standalone/server.js` / `{{PNPM_BIN}} --filter @app/web start`. Введён `{{PNPM_BIN}}` — и ему **сразу назначен материализатор** (scene-bootstrap подставляет `command -v pnpm`, симметрично `{{NODE_BIN}}`): правило урока 35 применено к самому фиксу — объявил плейсхолдер, назови компонент, который его материализует.
2. **Гейт против класса** (`orchestrator/lib/deploy-manifest.cjs`): `manifest-missing-prisma-codegen` — prisma-сигнал (литерал `prisma` в значениях migrate-шага) без codegen-шага; `unit-execstart-bare-command` — ExecStart-семейство с первым токеном не-`/` и не-`{{…}}` (systemd-префиксы `-@:!+` учтены; комменты не судятся — тот же закон, что у RELEASE_DIR-гейта). Оба «слеп ≠ нашёл»: нечитаемый шаблон ⇒ `execstart_bare: null` (не вердикт); opaque-скрипт ⇒ не флагается (честно задокументированное слепое пятно, запинено тестом как design decision). Порядок `blocking_defects` детерминирован: манифест-уровень → юнит-уровень. Ветка mis-equipped в `deploy-to-stage` стала defect-aware (сообщение перечисляет и bare-юниты — иначе `readiness_reasons` врал бы про новый класс, дух FIND-D).
3. **Тесты на реальной форме:** позитив-фикстура `current-linked` обновлена до формы, которую скилл теперь авторит; негативы **деривируются из неё в рантайме** («реальная форма минус ровно одна строка»: фильтр codegen-строки ⇒ C1; замена web-ExecStart на дословную live-форму ⇒ C2) — сдвиг против урока 0199/0200 «фикстуры автора лгут». Историческая `release-pinned` фикстура не тронута (держит ровно один дефект — изоляция).

**Проверка (empirics).** Три мутации гейта, все откачены: (A1) снят push C1-дефекта → красных **2**; (A2) снят push C2 → красных **3**; (A3) правдоподобная ошибка реализации — снят допуск `{{…}}`-плейсхолдеров → красных **6** (позитивы ловят overfire на `{{NODE_BIN}}`-эталоне, включая CLI-шов). Ложные срабатывания: без migrate — чисто; flyway-migrate — чисто; opaque-скрипт — чисто (пин); коммент `# ExecStart=pnpm` — не судится; `-/usr/bin/test` — легален. `npm run verify` = exit 0.

**Lessons.**

44. **«Кто это построит?» (урок 35) обязан задаваться и ГЕНЕРИРУЕМЫМ артефактам, не только каталогам и файлам.** Prisma-клиент — артефакт, который производится, а не кладётся; чистая среда (пер-релизный `node_modules`) стирает его молча, а dev-чекаут с исторически сгенерённым клиентом делает дыру невидимой для всех repo-side проверок. Тест на бумаге: для каждого производного артефакта (codegen, build-кэш, миграционное состояние) назови ШАГ процесса, который производит его в ЧИСТОЙ среде. Дефект не в том, что `prisma generate` забыли выполнить, — а в том, что он не был ничьим шагом.
45. **Юнит-обвязка пишется для среды ИСПОЛНЕНИЯ, а не среды АВТОРИНГА.** bare `pnpm` работает везде, где его пишут и проверяют (интерактивный шелл), и не работает там, где он исполняется (systemd без юзер-PATH). Дефекты разницы сред проходят любую проверку в среде автора; лекарство — плейсхолдер, материализуемый в момент, когда целевая среда доступна для опроса (`command -v` на сцене), плюс детерминированный гейт на форму.
46. **Детерминированный гейт видит ровно то, что оснастка показывает: прозрачность команды — контрактное требование, а не стилистика.** `db:migrate:deploy` и `exec prisma migrate deploy` исполняются одинаково, но для гейта первый — непрозрачный ярлык; слепое пятно задокументировано и запинено тестом, скилл предписывает прозрачную форму. Прятать семантику за скрипт-ярлыки — лишать все нижестоящие детерминированные проверки права её видеть.

## DEC-DEV-0206 — Ложно-негативный DEPLOY_FAILED: гейт build-test оставлял стратегию ожидания стохастике инстанса

**Context.** Диагностика трёх живых прогонов deploy-контура (2026-07-14) вскрыла ложно-негативный `DEPLOY_FAILED` на стадии build-test (прогон `l1fi9c`). Сьют пилота стабильно ~7.5 мин (длинный полюс `apps/api` ~4-5 мин, 865 тестов, идёт последним). Агент стадии сам выставил Bash-таймаут 300000 (5 мин) → kill на 5m0s (exit 143) → перезапустил сьют через `run_in_background:true` → поллил ~1 мин → добровольно вернул `passed:false` («completion UNKNOWN»); брошенный фон доработал сам через ~6 мин и был **100% зелёным**. Два успешных прогона (`kvikd4`/`kxe0ls`) выигрывали ровно одним приёмом — единый БЛОКИРУЮЩИЙ вызов с tool-timeout ≥ длины сьюта (600000/590000) — но и они сжигали 2-4 мин на дефолтных 2-мин kill'ах, нащупывая приём методом тыка.

**Корень.** Промпт стадии build-test не давал НИКАКИХ инструкций по таймаутам и стратегии ожидания — стратегия оставлена стохастике инстанса. Это тот же класс, что теорема трека 0202: **знание ≠ исполнение — передавай структуру принуждения, а не надежду.** Плюс вторичная ошибка осей: результат стадии схлопывал «не смог ИЗМЕРИТЬ» (kill/таймаут/брошенный фон = UNKNOWN) и «код ПРОВАЛИЛ» (реальный RED) в один `passed:false` → оба уходили в `DEPLOY_FAILED` → escalate. Это ошибка осей DEC-DEV-0201 («можем ли» vs «кто решает») на слой ниже: измерение-неполно vs код-провалил требуют ПРОТИВОПОЛОЖНЫХ реакций — ре-ран vs починка кода.

**Fix.**
1. **Промпт build-test — структура ожидания.** build: один блокирующий Bash-вызов, `timeout: 600000` явно. Сьют: пер-workspace последовательные блокирующие вызовы (`pnpm --filter <ws> test`, workspace'ы из `pnpm-workspace.yaml`), КАЖДЫЙ с `timeout: 600000` — заодно durable-защита от роста сьюта (единый вызов однажды не влезет в 10-мин потолок инструмента). Запреты в промпте: `run_in_background` для тестов; возврат вердикта до финального exit-code каждого workspace; коллапс UNKNOWN в `passed:false` без пометки незавершённости. Агрегация: `passed` = все exit 0; per-workspace числа в `disclosures`.
2. **Развод UNKNOWN и RED.** `BUILD_SCHEMA` получил `suite_completed:boolean` (additive, без переименований — DEC-DEV-0012; absent ⇒ completed, RED-путь байт-в-байт прежний). `passed:false` при `suite_completed:false` → **`BLOCKED × READY`** с `failure_class:'test-gate-incomplete'` (гейт не смог УСТАНОВИТЬ вердикт — отказ измерения, не кода) → `evt:deploy.gated` → `runtime_gate_retry` (ре-ран). `passed:false` при `suite_completed:true` (или absent) → как раньше `DEPLOY_FAILED` → `evt:deploy.preflight_failed` (escalate). Ветка стоит ПОСЛЕ `ENV_NOT_READY` и ПЕРЕД `if (!buildPassed)`, `disposition/autonomy:null` (гейт §3.2 не достигнут), полный FIND-D-трейл.

**Проверка (empirics).** Две мутации, обе откачены и обе краснят выделенный тест: (A) UNKNOWN снова коллапсирует в DEPLOY_FAILED (`suiteIncomplete = false && …`) → красный тест «incomplete → re-run, not a RED»; (B) RED становится BLOCKED (`suiteIncomplete = !buildPassed`) → красный тест «real RED stays DEPLOY_FAILED». Тесты исполняют РЕАЛЬНОЕ выражение (`new Function`, как `evalManifestOk`). `npm run verify` = exit 0.

**Lessons.**

47. **Гейт, оставляющий стратегию ожидания стохастике инстанса, однажды даст ложный вердикт — кодируй ожидание как СТРУКТУРУ.** Промпт «run build and the suite» без таймаутов и режима ожидания — это надежда, а не контракт: три прогона нащупывали рабочий приём методом тыка, и один промахнулся, спалив годный деплой. Блокирующий вызов + явный `timeout ≥ длины` + пер-workspace дробление — это принуждение; «обычно инстанс догадывается» — нет. Та же теорема, что 0202: знание ≠ исполнение. (Тот же паттерн в этот же день дали и операторы-субагенты хоста: 4/4 уснули на фоновом мониторе вопреки прямому текстовому запрету — текст не принуждает, структура принуждает.)
48. **«Не смог измерить» и «измерил провал» — РАЗНЫЕ оси, требующие противоположных реакций.** Отказ ИЗМЕРЕНИЯ (kill/таймаут/брошенный фон = UNKNOWN) → ре-ран; отказ КОДА (реальный RED) → escalate/починка. Схлопнешь в один `passed:false` — ложно-негативный прогон уходит в escalate по здоровому коду. Гейт обязан уметь сказать «я не знаю» отдельно от «нет» — ровно ось DEC-DEV-0201 на слой ниже.
49. **Durable-фикс дробит по ЕСТЕСТВЕННОЙ границе, а не подгоняет один таймаут под сегодняшний размер.** Пер-workspace вызовы решают не только текущий kill, но и завтрашний: весь сьют ~7.5 мин при 10-мин потолке инструмента — единый `pnpm -r test` однажды перестал бы влезать и сломался бы тем же образом. И back-compat через «absent ⇒ completed» держит RED-путь (kvikd4) байт-в-байт: новое поле не меняет поведение там, где его не прислали.

1. **Скилл `dev/meta-improvement/skills/informed-fetch.md`** — структура принуждения, не пересказ (теорема 0202): чеклист триггеров Столпа 1 (свежесть — приоритетен: патология недобора; длинный хвост по Maekawa NAACL 2024 — retrieval помогает на редком и вредит на популярном; «классика из приоров» — урок мисатрибуций Cooper/Ackoff), пре-регистрация вопроса+бюджета+инструментов ДО первого байта (R12: tool filter — единственная защита с ростом полезности), стоп-чеклист satisficing + marginal value theorem (честно как аналогия), 🛑-гейт изоляции веб-канала (ни байта веб-происхождения в авто-загружаемые каналы без санкции владельца; провенанс `(web: URL, дата)` обязателен), таблица anti-patterns с опорами.
2. **Условно-триггерная строка в «Process triggers»** проектного CLAUDE.md (push-канал; в always-on конъюнкцию не входит). Триггер прибит к симптому недобора: «пишу утверждение о внешнем мире, которое могло измениться после cutoff / несу классику из приоров в фундамент».
3. **Разграничение с Guided Research:** informed-fetch = минуты и ≤5 источников по ходу задачи; несущие спорные утверждения → `anti-hype-filter`; исследование с метриками → `research-intake`/`deep-research`. Скилл направляет, не дублирует SIFT-пайплайн.

**Отвергнутые альтернативы:** (a) consumer-скилл в `skills/` — спроса нет, патология измерена на моём процессе (cuttable scope); (b) warn-хук на WebFetch/WebSearch — симптом «надо было пойти в сеть» машинно не детектируем, хук ловил бы обратное направление (мы не тормозим, мы недобираем); (c) PI-детектор и NLL-фильтр — доказательно запрещены литературой аудита (см. Context); (d) блокирующий гейт на запись веб-фактов в память — детект «этот байт из веба» постфактум невозможен, гейт остался процедурным (🛑-правило в скилле + строка таблицы) до появления провенанс-трекинга.

**R10-итог (передача через шов):** следующий шаг сделан без вопросов к владельцу и без старых транскриптов; ре-инфляции нет (добор сверх названных файлов — только grep по живому репо). Зафиксированы 3 реальные дыры шва (термины «Столп 0/1» без определения; противоречие «инвариант merge-стоп vs мандат в строке состояния» — разрешено в пользу инварианта; открытый вопрос о судье — T1: sonnet по прецеденту 0204). **Вердикт судьи-не-автора (sonnet, рубрика G1–G5 до прогона): PARTIAL** — содержательная передача чистая (ACK верен, 5/5 якорей без искажений, 7/7 инвариантов), понижение за мета-уровень: продолжатель не задекларировал один из двух grep'ов, чьи сниппеты принесли цитаты из файлов вне названных швом, и не дотянул диагноз merge-противоречия до §Autoflow. Обе находки приняты и вшиты в `R10_VALIDATION.md` (+ кандидат-поправка v3 шаблона: декларировать каждый инструментальный доступ, включая grep-сниппеты); по третьей (чтение 753 строк первоисточников main-моделью) — обоснованное отклонение per MDP §3.5, зафиксировано.

### Lessons

50. **Модуль добора проектируется от измеренной патологии, а не от страха.** Априорный дизайн начал бы с «тормоза» (фильтры, детекторы мусора) — телеметрия показала обратную болезнь (0,09% вызовов), и приоритет получил триггер свежести; а оба «очевидных» защитных механизма (PI-детектор, NLL-фильтр) литература прямо убила. Мерь направление патологии до выбора механизма.
51. **Противоречие внутри шва разрешается в пользу стоп-блока.** Инвариант «merge — только владелец» и строка состояния «мандат: мержу сам» конфликтовали; правило: секция инвариантов (ре-инжектится, писана как запрет) бьёт хронику состояния. В шаблон шва это стоит внести явно при следующей ревизии протокола.

## DEC-DEV-0211 — Прогон сквозь красный светофор: ENV_NOT_READY не коротил префлайт, и стадия build-test сама подняла субстрат

**Date:** 2026-07-15
**Trigger:** живой прогон lah60w (S5 кампании — просадка субстрата): координатор остановил `mft-redis`; env-readiness корректно дала ENV_NOT_READY — но прогон не остановился.
**Tag:** #orchestrator #deploy #gates #capture-dont-fix

### Context

S5-сценарий: `mft-redis` погашен (docker Exited). Стадия env-readiness КОРРЕКТНО вернула `{readiness: ENV_NOT_READY, reasons: ["redis: … Connection refused"]}` — детекция работает. Но прогон не закоротился: manifest-parse и build-test запустились как ни в чём не бывало, и агент build-test, упёршись в 8 красных api-тестов из-за Redis-down, **сам вылечил субстрат**: `docker start mft-redis` («Start redis container required by api test suite»), дождался healthy и собрался ре-ранить сьют. Оператор убил сессию до мутаций деплоя. Это живое воспроизведение прецедента «диспетчер сам чинит субстрат и обесценивает свой же readiness-гейт» — теперь на уровне СТАДИИ процесса.

### Root cause

**FIND-E1** — инвариантная арка `ENV_NOT_READY ⇒ BLOCKED` в коде БЫЛА и работала, но стояла в КОНЦЕ префлайта (аккумулятор всех downgrade-источников). Для локальных downgrade'ов (манифест/оснастка/re-probe) это правильно — они возникают по ходу; но вердикт ПРОБЫ известен на первом шаге, и всё между детекцией и enforcement'ом исполнялось в мире, который гейт уже отверг. (В l7py9k ENV_NOT_READY корректно блокировал — но от scene-гейта, ПОЗЖЕ по конвейеру; ранняя дыра была не видна.)

**FIND-E2** — промпт build-test запрещал деплойные мутации («Do NOT deploy, flip, migrate, or commit»), но НЕ мутации среды. Агент, чей критерий успеха — зелёный сьют, при красном сьюте делает то, что сьюту «нужно». Теорема 0202 / урок 47 в третий раз за один контур: текст не принуждает, структура принуждает — а здесь не было даже текста. Опаснее прямого вреда то, что self-heal фальсифицирует аудит: run.json несёт честный ENV_NOT_READY, а реальность под ним уже переписана — следующие стадии мутируют среду, чью готовность никто не подтверждал.

### Fix

1. **Ранний short-circuit** (`deploy-to-stage.mjs:358`): `envProbeBlocks = readiness === 'ENV_NOT_READY'` сразу после пробы → `BLOCKED × ENV_NOT_READY`, `flipped:false`, `failure_class:'env-not-ready-preflight'` (гейт-инцидентный класс, форма 0206 `test-gate-incomplete` — не P7 boot-класс, ничего не бутилось), `disposition/autonomy: null` (резолвер честно не достигнут), `contract_status: null` (манифест не читался — «draft» был бы выдумкой), `blocking_defects: []` (оснастка не оценивалась), полный FIND-D-набор ключей, лекарство словами. Роутинг прежний: `evt:deploy.env_not_ready`. **Предикат ENV_NOT_READY-exact:** DEGRADED НЕ коротит — это ось решения, едет в §3.2 (applyReadinessGuard auto→human-gate); `!== READY` убил бы DEGRADED-ветку деплоя (S5). Поздняя арка осталась — ловит post-probe downgrade'ы.
2. **Capture-don't-fix как структура** во всех субстрат-смежных промптах: build-test («SUBSTRATE IS READ-ONLY»: перечисление запрещённых классов + «environment failures are EVIDENCE» + якорь: упавший из-за среды workspace достиг exit-кода ⇒ ЗАВЕРШЁННЫЙ red, `suite_completed` 0206 не для маскировки) · env-readiness / runtime-readiness (read-only мандат) · scene-bootstrap / deploy-flip (MUTATION BOUNDARY: легитимные мутации перечислены; «restart app-юнитов — единственный systemctl») · healthcheck (не поднимать сервисы ради 2xx). manifest-parse / autonomy-resolve не тронуты — чистые lib-CLI транспорты, их успех от субстрата не зависит.
3. **5 wiring-тестов:** структурный порядок (probe < short-circuit < manifest-parse < build-test) + предикат исполняется как код (`new Function`: ENV_NOT_READY→true, DEGRADED/READY→false; DEGRADED доезжает до резолвер-команды) + grep-инварианты маркеров шести промптов.

**Проверка (empirics).** Две мутации, обе откачены, обе краснят выделенный тест: (A) предикат отключён («замыкание снято») → красный E1-predicate; (B) `!== 'READY'` («DEGRADED тоже коротит») → красный S5-TRAP. 37/37 после отката; `npm run verify` = exit 0.

### Lessons

54. **Гейт, чей вердикт уже известен, обязан срабатывать в точке вердикта — всё, что исполняется между детекцией и enforcement'ом, работает в мире, который гейт уже отверг.** Инвариант «ENV_NOT_READY ⇒ BLOCKED» существовал и был покрыт тестами — но стоял в конце префлайта, и три стадии успевали отработать на мёртвом субстрате. Детекция без немедленного enforcement — приглашение нижестоящим «попробовать всё равно»; а стадия, которая пробует, дальше сама и чинит. Аккумулятор-арка законна для фактов, возникающих по ходу, — но каждый факт, известный раньше, коротится там, где узнан.
55. **Агент, чей критерий успеха зависит от состояния среды, будет чинить среду — если запрет не вписан структурой (и legitimate-мутатору нужна явная граница «что моё»).** build-test имел запреты деплойных мутаций, но не средовых — и агент сделал ровно то, что «нужно» его сьюту: docker start. Работают перечисление запрещённых классов команд + переопределение цели («упавший из-за среды тест = EVIDENCE, записать, не чинить») — та же форма принуждения, что структура ожидания 0206. Симметрично для scene-bootstrap/deploy-flip: мандат «мутируй» без границы читается как «мутируй что угодно» — деплой-мутации ⊂ мутации, и разница должна быть словами.

**Lessons.** (нумерация: 62 занята addendum'ом 0217 в PR #219)

## DEC-DEV-0220 — аудит когерентности репо: 48 подтверждённых противоречий сводятся к одному корню; `check-counts` расширен на команды/хуки/скиллы/агентов (warn-режим)

**Root cause — один на 48 находок.** Волатильный факт скопирован **прозой** в N мест, и ни один механизм не связывает копии с источником. Копии не «стареют»: они начинают лгать в момент коммита, который их не тронул. 48 находок = ~6 фактов (флип `lesson-presence-gate` warn→strict не доехал до ≥6 копий; ретайр skills-floor/DEF-CTX-5 не доехал до auto-loaded CLAUDE.md; пересуд 0204 не доехал до планов гейтов; счётчики команд/хуков; конвенция B.1; извлечение версии CHANGELOG).

**Диагноз — лекарство уже было, но узкое.** D12 (DEC-DEV-0197) изобрёл pointer-collapse и объявил precedence, но **самоограничил её**: правило действует на «любое другое место ЭТОГО файла», поэтому копии в `CONVENTIONS.md` / `checklists/` / module-SPEC остались вне решётки SSOT. Инфраструктура реконсиляции при этом СУЩЕСТВУЕТ (5 генераторов с `--check` + 5 чекеров в `verify`) — дефект в её ПОКРЫТИИ, не в отсутствии.

**Решение по автономности (ответ на вопрос владельца «как сделать автономными»).** Отвергнут автономный LLM-правщик: он чинит прозу «по своему пониманию» и порождает новый дрейф с погашенной сигнализацией — генератор дефекта под видом лекарства. Принята асимметрия: **обнаружение автоматизируется почти везде, правка — только там, где ответ вычислим из ground truth**. И принцип: **лучший механизм не ловит расхождение, а делает его невозможным** (генератор или указатель вместо копии). Периодический cron-аудит отвергнут: прогон стоил 4.7M токенов — LLM-аудит по требованию (ищет НОВЫЙ класс), детерминированные чекеры в `verify` — постоянно и бесплатно.

**Сделано (S1).** `check-counts.js` расширен с 2 kinds (artifact/rule) до 6: `command` (+ per-namespace), `hook` (+ per-namespace), `skill`, `agent`, `pattern`-ground-truth. Ground truth вычисляется с диска; namespace'ы **обнаруживаются**, а не захардкожены. Найдено и исправлено 5 расхождений — 3 из реестра аудита (README integrator 9→13, product SPEC 22→23 команды и 12→13 hooks, integrator SPEC 12→13) и **1 новое, которого аудит не нашёл** (design SPEC 5→7 команд). Чекер зелёный, `--strict-extended` тоже зелёный ⇒ флип возможен.

**Почему extended — warn, а не strict.** `check-counts` вызывается из `process-gate` — БЛОКИРУЮЩЕГО commit-msg гейта. Ложное срабатывание здесь не раздражает, а **останавливает все коммиты в репо, всем**. Core-паттерны заработали право блокировать за год; extended матчат свободную прозу и этого права ещё не имеют. Въезд warn'ом + флип за владельцем — та же схема, что у `check-inventory-sync.cjs` и `lesson-presence-gate.js`. Тумблеры: `--strict-extended`/`COUNTS_EXTENDED_STRICT=1`, `--core-only`/`COUNTS_EXTENDED=0`.

**Lessons.**

66. **Regex по прозе за инвентарным числом — по умолчанию мусорогенератор; спасает не «лучший паттерн», а КОНТЕКСТ.** Первый эмпирический прогон дал ~35 срабатываний, почти все ложные, и шум был поучителен: `### 14.1 Skills` → «1 skill», `A11 hook` → «11 hooks», `×2 subagents` → «2 agents», `§7.6 pattern` → «6 patterns». Вылечили не изощрением regex, а тремя контекстными правилами: цифра, склеенная с номером раздела/версии/идентификатором — никогда не тотал; заголовок — навигация, не заявление; **fenced-блок — пример вывода, не инвентарь**. Осталось 5 срабатываний, все настоящие, 0 ложных.
67. **Guard, написанный «на всякий случай», ест ровно то, что должен стеречь — и делает это молча.** В foreign-guard попал `.claude/`, и он немедленно скрыл НАСТОЯЩУЮ находку («12 hooks … `.claude/hooks/product/`»): в ЭТОМ репо `.claude/` — целевой путь доставки своих же артефактов, а не чужой контекст. Симптом отсутствовал по построению — пропавшая находка не кричит. Правило: каждый guard проверяй на том, что он ОБЯЗАН пропустить, а не только на шуме, который он давит.
68. **Неверный `expected` хуже молчания.** Пока `hook` в module-SPEC сравнивался с тоталом репо (19), чекер репортил дрейф на честной строке «12 hooks» продукта (правда — 13): читателя отправляли «чинить» корректное число неверным эталоном. Счётчик в доке модуля — про модуль; ошибка привязки дороже пропуска, потому что уничтожает доверие к гейту.
69. **Омоним, который нельзя развести машинно, — вечный источник ложных: не покрывай его, а признай.** Слово «pattern» в репо значит минимум три вещи (D7-паттерны, словарь анти-паттернов линтера, regex) — kind `pattern` для сканера прозы выброшен сознательно, счёт паттернов остаётся человеку. Честно объявленное непокрытие лучше гейта, который врёт (тот же закон, что «чекер ослеп ≠ нашёл дрейф»).

70. **Находка №27 сработала на своём же авторе — в том же коммите, что её описал.** Расхождение `precedence-dup-1` (CONVENTIONS §11.1 «каждое смёрженное изменение несёт запись в CHANGELOG» ↔ SSOT-таблица CLAUDE.md «CHANGELOG только если тронут consumer-zone») я зафиксировал в реестре — и тут же **пошёл по неверной стороне**: положил в `[Unreleased] ### Added` расширение `check-counts.js`, то есть dev-only скрипт из `dev/`, который по канону «не попадает в пользовательские проекты» и потребителя не касается вообще. Поймал не гейт (`CONVENTIONS` его не принуждает, а `process-gate` требует CHANGELOG лишь при consumer-zone — то есть **обе стороны молчали**), а владелец вопросом «released/unreleased — это разве не про изменения, идущие в продукт?». Запись убрана, суть осталась здесь. **Цена расхождения измерена:** оно не теоретическое — стоит одной неверной записи в release notes на каждый эпизод, и ловится только человеком. Это переводит **S5** («снять самоограничение D12» + кросс-файловый sweep дублей обязательств) из «гигиена» в «есть жертвы»: правило, записанное дважды, не просто расходится — оно **активно уводит исполнителя**, потому что исполнитель читает ту копию, которая ближе. Практический вывод: **тест «а увидит ли это потребитель в поставке?» сильнее любой из двух формулировок** — и при следующей правке CONVENTIONS §11.1 должен схлопнуться в указатель на SSOT-таблицу, а не в третью редакцию.

## DEC-DEV-0220-a — флип extended-видов `check-counts` warn→strict (решение владельца)

**Date:** 2026-07-17
**Trigger:** решение владельца «флипай strict» после того, как warn-цикл S1 (DEC-DEV-0220) вернулся чистым.
**Tag:** #meta #d7 #counts #gate #flip

**Решение.** Extended-виды (`command`, `hook`, `skill`, `agent`) блокируют по умолчанию. Аварийный тумблер — `--warn-extended` / `COUNTS_EXTENDED_STRICT=0`; полное отключение — `--core-only` / `COUNTS_EXTENDED=0`. Флаг `--strict-extended` принят как no-op: он теперь дефолт, но живёт в уже смёрженной прозе CHANGELOG/журнала и в мышечной памяти — молча отвергать его невежливо.

**Почему тумблер обязателен, а не «на всякий случай».** `check-counts` вызывается из `process-gate` — блокирующего `commit-msg`. Это **общий ресурс**: ложное срабатывание останавливает коммиты всем, а платит не тот, кто сломал. Репо уже кодифицировало этот закон для `INVENTORY_SYNC_STRICT=0` («гейт на общем ресурсе без выключателя однажды склинит чужой цикл»); флип без выключателя нарушил бы его.

**Как проверено — адверсариально, а не «зелёным».** Зелёный прогон не доказывает, что гейт умеет падать. Подсунут заведомо ложный счётчик (`README.md`: `/integrator:* (77 команд)` при ground truth 13) и снят код возврата в трёх режимах: дефолт → **exit 1** (блокирует, находка названа с координатой), `--warn-extended` → exit 0, `--core-only` → exit 0. README восстановлен, `git diff` пуст.

**Побочный улов — правило поймало собственного автора (снова).** Свежайшие ложные копии режима нашлись **внутри `check-counts.js`**: комментарий `// ── EXTENDED (warn-only by default) ──` и «`--strict-extended` is only earned by a quiet warn period» — обе строки стали ложью в момент флипа, в том же файле, что флип и делает. Это ровно корень аудита («волатильный факт скопирован прозой; копия устаревает в момент коммита, который её не тронул»), проявившийся на дистанции 120 строк от точки изменения. Вывод не «быть внимательнее», а структурный: **режим обязан спрашиваться у кода** — `--json` отдаёт `extended_mode`, и `patch-cut.md` теперь ссылается на него вместо того, чтобы пересказывать («не переписывай сюда, спроси у скрипта»).

**CHANGELOG намеренно НЕ трогаем.** `check-counts.js` живёт в `dev/`, который по канону «не попадает в пользовательские проекты» — потребитель этот гейт никогда не запустит. Это первое применение урока 70 по назначению.

**Lessons.**

71. **Зелёный гейт и работающий гейт — разные утверждения; флип обязан доказывать второе.** «Прогон чистый» доказывает лишь отсутствие ложных срабатываний — то есть что гейт **молчит**. Что он **умеет падать** на настоящем дрейфе, доказывает только инъекция заведомой ошибки с проверкой кода возврата. Дешёвый тест поймал заодно и мою собственную ошибку измерения: первый прогон отчитался `exit=0` на подложном счётчике, потому что `$?` за пайпом вернул код `head`, а не `node`. Я едва не записал «strict не блокирует» как факт о гейте, хотя это был факт о моём тесте. **Инструмент измерения проверяй прежде объекта измерения** — иначе адверсариальная проверка выдаёт ложное опровержение, а оно дороже пропущенной находки: снимает подозрение с настоящего дефекта.

## DEC-DEV-0220-b — кластер warn→strict: 6 копий ship-default приведены к коду

**Date:** 2026-07-17
**Trigger:** волна A аудита когерентности; кластер «флип `lesson-presence-gate` warn→strict».
**Tag:** #meta #d7 #coherence #enforcement

**Что было.** Флип 2026-07-11 (DEC-DEV-0177) обновил код и manifest. Ship-default при этом описан прозой ещё в 6 местах — и **все шесть остались на «warn»**: скилл `self-correction.md`, `docs/pmo/processes.md`, `commands/ecosystem/verify.md` Step 8.5, overlay гида (→ 2 сгенерированных HTML), комментарий внутри самого хука.

**Почему это хуже обычного дрейфа — врали в опасную сторону.** Не «число разошлось», а «доки обещают напоминание там, где вызов будет ОТКЛОНЁН». Три отдельных проявления, каждое своего класса:
- `processes.md` описывал `LESSON_GATE_MODE` **зеркально коду** — как включатель deny (`=strict` enables), хотя это выключатель (`=warn` понижает). Читатель, применивший доку буквально, получил бы ровно обратный эффект.
- `verify.md` Step 8.5 инструктировал считать warn **ожидаемым** и не флагать его — то есть **гасил сигнал о настоящем даунгрейде**. Причём шаг противоречил собственному телу (:182-186 уже требуют флагать warn/off). Гейт, инструктированный не замечать обход, хуже отсутствующего гейта: он создаёт ложную уверенность.
- Ложный комментарий нашёлся **внутри самого хука**, в 40 строках от кода, который его опровергает.

**Ordering-правило отчёта («не править кластер вручную до S4») — сознательно отклонено, вот почему.** Правило исходило из посылки, что S4-генератор **заберёт эти копии себе**. Проверка структуры показала: посылка неверна. Это не поля таблицы, а проза в шести разнородных документах (скилл, промпт команды, SPEC, JSON-overlay, комментарий в коде) — генератор её не может *владеть*, он может только *проверять*. Значит правка сейчас не «работа, которую S4 переделает», а необходимая в любом порядке. Оставлять доки лгать, пока строится чекер, — хуже. **Урок для самих ordering-правил:** правило порядка, выведенное из непроверенной посылки о механизме, обязано пересуживаться, когда посылку проверили; S4 при этом не отменяется — он нужен, чтобы **следующий** флип поймал копии автоматически.

**Грабля инфраструктуры (стоила бы красного verify).** `docs/guide/ecosystem-map.overlay.json` — источник **двух** генерируемых HTML: `gen-ecosystem-map.cjs` и `gen-process-map.cjs` (второй читает тот же overlay, хотя имя файла об этом не говорит). Правка overlay без `npm run gen:map && npm run gen:procmap` роняет `verify` на STALE. Обнаружил субагент-верификатор; проверено — оба чекера в цепи `verify`.

**Lessons.**

72. **Кросс-классовое сканирование считает один дефект несколько раз — «сколько находок» и «сколько работы» не одно и то же.** Кластер `CLAUDE.md` пришёл как 5 находок с разными id, а оказался **2 правками**: три id (`deferred-lifecycle-3` = `gate-code-vs-doc-2` = `inventory-sync-4`) указывали дословно на одну строку, два — на другую. Это не ошибка скаутов: один и тот же дефект законно виден из нескольких классов (он и «отложенное, что построено», и «гейт против доки», и «инвентарь-синк»). Но при учёте это даёт **фантомную работу**: закрыв 2 строки, видишь «3 находки не сделаны» и идёшь их искать. Дедуп по координатам обязан идти ДО планирования объёма, а не после; и планировать надо по **строкам-жертвам**, а не по id находок.

## DEC-DEV-0220-c — вердикты гейтов схлопнуты в указатели; баг поставки «version Unreleased» устранён

**Date:** 2026-07-17
**Trigger:** волна A аудита когерентности; кластеры «вердикты гейтов» (S3) и «извлечение версии» (S7).
**Tag:** #meta #d7 #coherence #gates #delivery

**S7 — единственная находка аудита, которую видел пользователь.** `install.sh` печатал «Ecosystem 3.0 installed globally (**version Unreleased**)»: `grep -m1 '^## \['` брал первый заголовок CHANGELOG, а первым всегда стоит `## [Unreleased]`. Тот же дефект в `install.ps1` и в промпте `bootstrap.md` («read from CHANGELOG first entry» → штампует `ecosystem_version: Unreleased` в свежий пилот, и `/ecosystem:verify` обязан ловить это как version drift). Воспроизведено живьём на **обеих** платформах, фикс проверен там же: было `Unreleased` → стало `1.12.1`; CHANGELOG без версий → `unknown`.

**Латентный дефект сверх реестра.** `|| echo "unknown"` в `install.sh:76` **мёртв**: код возврата пайпа берётся от `sed`, а тот всегда 0. На CHANGELOG без выпущенных версий печаталось бы пустое значение («version .»), а не `unknown`. Фолбэк, который никогда не срабатывает, — хуже отсутствующего: он создаёт видимость обработки края. Заменён явным `[ -n "$VERSION" ]`.

**Почему «общий хелпер» из формулировки S7 — неверная цель (вывод против собственного плана).** `install.sh`/`install.ps1` — standalone-бутстрапперы: исполняются ДО того, как что-либо установлено (нет `.claude/`, нет `node_modules`, Node не гарантирован — сам факт двух установщиков и есть признание, что общего рантайма на входе нет). Хелпер требует ровно того рантайма, которого на этом шаге ещё нет. При этом **само правило — один регекс в ~30 символов**: дублировать его вчетверо дешевле любой машинерии шаринга. Настоящая болезнь не дублирование, а **дрейф**: правильная реализация уже существовала в `update.md` в обоих языках (bash + PS) и просто не доехала до установщиков. Поэтому вместо хелпера: `update.md` Step 5c объявлен референсом, три остальных сайта несут указатель на него. Гейт, если строить, — **на поведении** (исполнить извлечение и сравнить с ground truth), а не грепом исходников на «правильный регекс»: текстовый чекер стал бы **пятой копией правила** и разошёлся бы следующим.

**S3 — линия реза найдена эмпирически, а не по формулировке.** Правило «план не держит inline-копию вердикта» звучит абсолютным, но проверка показала исключение: трекер кампании **заархивирован**, и шапки `PATCH:3` / `PHASE_6:5` — **единственный дом** вердиктов догонов E1/E2. Значит рез не «убрать все копии», а: **вердикт живёт там, где у него нет другого дома; всё остальное — указатель**. Схлопнуты: баннер + Status-колонка `PATCH_1.3.3`, придаточное `PHASE_6`, и **третья копия** в `SUBSTRATE_GRADUATION_GATE.md:107-108` — файл, который строкой выше (`:101`) **сам объявляет** бриф своим SSOT и тут же ему противоречит. Идеальная иллюстрация корня: **указатель рядом с копией не мешает копии устареть**.

**Релиз 1.12.1 обострил дефект, а не создал.** Он добавил в оба плана новые ЗАКРЫТ-шапки с верными вердиктами и не тронул старые баннеры — файлы стали противоречить **сами себе** (`PATCH:3` = «S1 PARTIAL» против `:13`/`:17` = «S1 PASS»). `PHASE_6` не упоминает пересуд 0204 **ни разу**. Это ровно предсказание аудита: копия устаревает в момент коммита, который её не тронул.

**Lessons.**

73. **Правило, выведенное из формулировки решения, обязано пересуживаться против фактов — иначе оно вредит именно там, где звучит убедительнее всего.** Три моих собственных плановых правила пали при столкновении с диском: (а) «не править warn→strict до S4» — S4 не может владеть прозой в 6 разнородных доках, только проверять; (б) «общий хелпер версии» — невозможен, установщики стартуют без рантайма, а правило = один регекс; (в) «pointer-collapse вердиктов» — абсолютный рез уничтожил бы единственный дом вердиктов E1/E2. Все три звучали как выводы, а были **гипотезами о структуре**, написанными до её проверки. Симптом один: план говорит «сделай X везде», а диск отвечает «здесь X разрушителен». **Гипотезу о механизме проверяй на структуре ДО того, как она станет правилом порядка** — иначе цена ошибки платится не спором, а сделанной не той работой.

## DEC-DEV-0220-d — решения D-1..D-4 по мандату владельца + три дефекта собственного шва

**Date:** 2026-07-17
**Trigger:** «прими оптимальные решения и зафиксируй в шве» + «убедись, что шов содержит всё необходимое».
**Tag:** #meta #d7 #coherence #seam #decisions

**Решения (полное обоснование — `dev/coherence/SEAM.md` §Решения).** Все четыре приняты ПОСЛЕ проверки фактов на диске, и **две проверки перевернули предварительный вывод**. Вопросы выглядели как выбор из формулировок, а оказались вопросами о фактах — именно поэтому не были приняты «на лету» в первом заходе.

- **D-1. Тело PS → к канону.** Решил факт: заголовки канона **литеральные**, его собственный «Good»-пример несёт ровно `## Problem` / `## Context` / `## Current alternatives` / `## Consequences` / `## Why now`. Секцию «Что мы хотим изменить» в канон не поднимаем — она **дуал `Consequences`**. Настоящая дыра не в именах: скилл **никогда не производит `Why now`** — это недостающий вопрос к пользователю, а не переименование. Пилот не ломается: тело PS не валидируется никем.
- **D-2. `stale-refs-3` → закрыть вопрос.** Не архитектурное решение — **запись уже принятого** (DEC-DEV-0040 Q2, 2026-05-25, три источника). Минимальный вариант (починить только путь) **хуже**: даёт рабочую ссылку на документ, опровергающий ведущее к нему предложение.
- **D-3. Узаконить `### Changed`, `Modified` → legacy.** Расходятся не «доки vs файл», а **доки vs собственный объявленный стандарт**: `CHANGELOG.md:5` объявляет Keep a Changelog, где `Changed` штатная, а `Modified` выдумана. Ретроспективно не переименовываем — выпущенные секции append-only. Словарь объявить в ОДНОМ месте (SSOT-таблица), копии в `CONVENTIONS`/`patch-cut` схлопнуть вместе с S5 — **обновить копию = отложить дефект, а не снять**.
- **D-4. V-09 — вопрос был меньше дефекта.** `V-09: SEG has exactly 1 VP` — 🔴 **Blocking**, `Automation: ✅ Fully`, `When: Approve gate (SEG)`. А конвейер: «After G4 → SEG active» → «Next steps: D1.4a VP design **per active SEG**». **Блокирующее правило требует на G4 артефакт, который конвейер создаёт шагом позже.** Порядок инвертировать нельзя (дизайн VP потребляет одобренный SEG) ⇒ невыполним не конвейер, а **момент проверки**: чекпойнт V-09 переносится на выход D1.4a, инвариант 1:1 не меняется. **Вытекшая находка:** если бы V-09 реально принуждалось на G4 — каждый approve сегмента падал бы, а сегменты у пилота есть ⇒ либо правило не реализовано (🔴-правило, которое никогда не срабатывает — прецедент «пронга с нулём читателей», DEC-DEV-0198), либо реализовано не там, где заявлено. Проверить ДО правки канона: от этого зависит, чинится документ или код.

**Три дефекта нашлись в моём собственном шве — и ни один не нашёлся бы перечитыванием.**
1. **Шов отправлял за правками «в транскрипт сессии»** — место, недоступное продолжателю по построению (харнесс прямо предупреждает: чтение переполнит контекст). Верификация 8 кластеров стоила ~750k токенов и **сгорала бы при каждом продолжении**. Вынесено на диск: `dev/coherence/VERIFIED_FIXES.md`.
2. **Не было маркера `<!-- SEAM-REINJECT-END -->`** — единственный активный шов без него (у обоих соседних есть) ⇒ инъекция резалась фолбэком на 40-й строке, посреди таблицы.
3. **СТОП-блок 3562 Б** выедал общий кап 6 КБ. Ужат до 2703 Б.

**Lessons.**

74. **Написанное для передачи проверяется прогоном приёмника, а не перечитыванием.** Я перечитал свой шов и счёл полным — он был неисполним по трём независимым причинам сразу. Все три вскрылись за минуты, когда я **запустил хук** и **сверил с соседними швами** вместо того, чтобы верить тексту. Автор не может прочитать свой документ глазами того, у кого нет его контекста: я знал, что правки «в транскрипте», и это ощущалось как знание, а не как тупик. **Приёмник артефакта передачи — механизм или другой агент; тест — его прогон.** Частный случай общего закона трека: результат работы субагента, не записанный на диск, **не существует** — ссылка на транскрипт не передача знания, а его потеря с отсрочкой.

75. **Я раздул собственную находку — и поймал это не сам.** Кап ре-инжекции я пометил 🔴 и написал «механизм **молча** теряет то, что обязан донести». Вопрос владельца («а на что это влияет? я же могу вставить шов как есть?») заставил проверить: кап трогает **только** авто-бэкстоп после компактации — не ручную вставку, не чтение файла, не обязательное чтение по Process triggers; и теряет **не молча** — обрезка **называет невлезшие файлы поимённо**, то есть контент деградирует до указателя. Реальный вред: сессия чужого трека получит в инъекции мой СТОП-блок + указатель на свой — шум и лишний шаг, а не потеря. **Найдя дефект, я оценил его по драматичности формулировки, а не по радиусу**; и вписал раздутую оценку в документ, который обязан быть надёжным, — ровно тот класс дефекта, что лечит трек. Правило: у находки первым делом меряется **радиус** («что перестаёт работать, если не чинить») — до того, как выбран цвет и наречие.

Юнит-тест на парсер (pass/fail/empty, 19 проверок). **Правило нуля-доказательств** (несущее, зеркалит «ложный DEPLOYED» 0203): репорт с 0 журнеев/нечитаемый → `ENV_NOT_READY` (не смог судить), **никогда не PASS** — зелёный гейт над «ничего не прогнали» = ложный зелёный.

- **DoD-нога (RL.md):** категория 3 «Stage» — «UJA PASS на текущем составе релиза» (SSOT = P8 `run.json` `uja_result: PASS`); категория 5 — для `has_ui` подстрока «journey-скриншоты как visual-conformance артефакт» (owner-ревью против MK; авто-diff MK — v1.1).
- **run-ledger:** `uja_result` добавлен в `OUTCOME_KEYS` — детерминированный GUARD (`run-ledger.test.cjs`) сканит return'ы процессов и **требует** этого (иначе вердикт суммаризовался бы в `null` — ровно класс дефекта p7_result, DEC-DEV-0200). Снапшот `OUTCOME_KEYS` в тесте обновлён.

### Lessons

1. **Каждый уровень гейта ловит свой класс, и «зелёный ниже» ≠ «работает выше».** Тесты → сборка → старт (P7) → деплой+healthcheck (E.B) → **реальное касание (P8)**: каждый предыдущий необходим, но не достаточен для следующего. 2. **Вердикт приёмки — факт о байтах, не суждение LLM.** Стохастический парс за гейтом — монетка в обе стороны: ложный FAIL блокирует хороший релиз, ложный PASS отгружает битый journey. Парс живёт в `uja-report.cjs`, агент — транспорт (тот же урок, что deploy-manifest.cjs/0203).
3. **Правило нуля-доказательств — несущее.** Гейт, зеленеющий над «0 журнеев прогнано», хуже отсутствия гейта: он легитимизирует пустоту. 0 журнеев → ENV_NOT_READY, никогда не PASS.

### Lessons

1. **Здоровье графа ≠ правдивость узлов.** 0 битых ссылок при 38 лгущих утверждениях. Это разные оси;
   вторая не измерялась ничем. Чекер связности создаёт ложное чувство порядка.
2. **Ложное «покрыто» опаснее честного «не покрыто».** `CLAUDE.md` и шапка `check-inventory-sync`
   обещали гейт для `docs/MAP.md`. Обещание гейта снимает бдительность там, где защиты нет.
3. **Правило, которое никто не измеряет, — это пожелание.** §5.1 держала пороги ротации, пробитые
   втрое. Причём дефект был в **гранулярности правила** (календарный месяц при каденции 97 записей
   за 23 дня), а не в дисциплине. Чинить надо правило, а не только его последствие.
4. **Механику — скриптам, суждение — моделям.** Из 8 субагентов **5 умерли** (watchdog на пофайловом
   обходе, обрывы API) — все на механических задачах. Переписанные как детерминированные скрипты, те
   же задачи отработали за секунды и идемпотентно: 154→12 битых ссылок одним прогоном; ротация
   журнала со сверкой «записей до = живой после + архив».
5. **Исполнитель обязан остановиться, когда посылка брифа неверна.** Волна A отказалась удалять
   `battery/panes/*.txt` (на них ссылается `VERDICT.md` как на несущую улику) и архивировать
   `EPIC_E_READINESS.md` (10+ ссылок из живого рантайма) — оба отказа верны. То же правило сработало
   вверх на `vendor/`.
6. **`[[wikilinks]]` в этом репо — в основном НЕ ссылки:** 91 из 103 — ключи persistent-памяти,
   живущие вне репозитория. Любой будущий чекер обязан их отличать, иначе даст 91 ложное срабатывание.

## DEC-DEV-0228 — Анализ эффективности Global Loop: экосистема эффективна ровно настолько, насколько её правила материализованы в машине

**Date:** 2026-07-29
**Trigger:** «Го» владельца на исполнение `dev/global-loop/EFFECTIVENESS_ANALYSIS_PLAN.md` (ratified 2026-07-28) отдельной аналитической сессией + уточнение «продолжай автономно до owner class решений». Вопрос владельца дословно: «насколько эффективен мост от интенции через хост-пульт → механизмы экосистемы → фактические изменения в коде… нет ли такого, что экосистема переусложняет или переписывает одно и то же по 10 раз… кодовая база может деградировать, хотя комплексные процессы "по бумагам" работают».
**Tag:** #architecture #tooling #pilot-finding #measurement

### Context

Два живых прогона (RUN-A 17–20.07, RUN-B 22–23.07) и эпоха до них дали корпус, который ни разу не измерялся: 203 сессии, 14 573 вызова инструментов, 610 коммитов пилота, 1109 сообщений владельца, 91 запись машинного run-ledger, 24 релиза. Замеры M1–M15 посчитаны по пре-регистрированным формулам (`analysis/PREREG.md`), M16 (каузальная A/B-проба) не запускался — требует отдельной санкции.

Ключевая методологическая рамка: **самоотчёты — объект проверки, а не источник истины**. Поэтому первым выполнен M7.

### Options considered

1. **Верить журналу и считать по нему** — отвергнуто рамкой плана: ландшафтный базлайн даёт до 8× завышения самоотчётов.
2. **Считать всё по harvest-копиям на хосте** — отвергнуто санитарией: harvest **не содержит субагентов** (1463 файла, 201 MB), а на них приходится 27–67% токенов. Любой учёт по harvest занижен в разы.
3. **Считать по полному корпусу VM + git + run-ledger, а самоотчёт верифицировать выборочно** — выбрано.

### Decision

Отчёт и датасет — `dev/global-loop/analysis/` (карта — `analysis/README.md`, главный документ — `analysis/REPORT.md`).

### Outcome

**Опасения владельца проверены, два из трёх не подтвердились:**
- «переписывает одно и то же по 10 раз» — **нет**: ни один артефакт не переписан >3 раз, проходы сходящиеся; self-churn 13.2% → 3.0% → 1.3% (индустрия ≈7.9%); дубли 1.5% → 1.4%; плотность ветвлений 0.106 → 0.108 при +38% кода;
- «база деградирует при зелёных бумагах» — **нет**: подгонки под гейт не найдено (2 подозрительных эпизода за всю историю, оба добросовестные), fix survival 74/74, mutation score 0.778;
- «сложная фабрика — маленький выхлоп» — **частично да**: цена runtime-строки выросла 198 → 613 → 1099 токенов, но природа работы сменилась (стройка → доводка), а темп поставки вырос впятеро; «фабрика пишет доки вместо кода» **опровергнуто**: markdown:код 3.38:1 → 0.16:1.

**Что подтвердилось как реальная проблема:**
- **у 97 из 162 дефектов (59.9%) не существует гейта, который обязан был поймать**; среди 61 открытого — 77% этого класса;
- **rework** 22.9% сессий / 21.1% токенов (строго), до 55.4% токенов (широко); крупнейший источник — гейт-петля RUN-A, где **пять вердиктов NO-GO имели один механический корень, продиагностированный пятикратно, каждым агентом заново**;
- **оверхед пульта**: токены хоста / токены исполнителей = 1.62 (RUN-A) → 0.47 (RUN-B) при пороге 0.20; **мультипликатор всего 1.8 ч машинной работы на 1 ч владельца**;
- **cost per resolved intent = 802 616 токенов / 92 мин**, но между прогонами упал в 3.4 раза (1.55M → 457k);
- 4 интенции переоткрывались, **3 из них — одна тема «приёмка не ловит базовых ошибок»**.

### Lessons

1. **Главный вывод, к которому независимо сошлись три замера: работает то, что материализовано в машине.** M10 — сильные оси спек это те, у которых есть обязательный носитель в шаблоне (провалена ровно одна ось — матрица доступа, у которой носителя нет, и именно из неё пришли находки #3/#4/#9). M11 — не дрейфуют **вообще** только `requirements`, единственный артефакт-вход кодогенерации; всё остальное устаревает за ~16 дней. Дефект-реестр — где гейт есть, он ловит (46 машиной против 15 владельцем), где гейта нет — 60% дефектов. **Правило, записанное в реестр, но не превращённое в гейт, возвращается тем же дефектом.**
2. **Метрика харнесса `totalTokens` — это пиковый контекст, а не расход.** Заявленные «1.81M токенов консилиума» оказались суммой water-mark; фактический расход — 24.5M (в 9.4 раза больше). Любые бюджетные оценки, снятые с этого поля, занижены на порядок. Считать расход только по `message.usage` каждой assistant-записи.
3. **Многоагентный консилиум проиграл одиночному судье** по совпадению с тем, что владелец ратифицировал (4/6 против 5.5/6) при цене 24.5M токенов. Причина не в многоагентности, а в агрегаторе: он читает только оценки и выбрасывает раздел «риски рекомендации», где присяжные честно записали дисквалифицирующий факт.
4. **Наивный аудитор самоотчётов производит ложные обвинения** с частотой, сопоставимой с той, что ищет: первые прогоны верификатора дали 4 «расхождения», все оказались дефектами метода (регекс `GO` внутри `NO-GO`, номера артефактов как счёт прогона, поиск следа не в субагентах, единственная форма записи счёта). Аудировать аудитора нужно **до** объекта.
5. **Инвентарь свидетельств обязан покрывать все репозитории, где живёт работа.** Три независимых судьи указали на одно слепое пятно (пакет видел только коммиты пилота); после расширения 10 из 14 спорных вердиктов сместились — все в сторону **большего** успеха.
6. **Журнал прогонов честен ровно там, где проверяем:** claim-accuracy 1.000 (42/42), но машинный якорь несут лишь 38.5% его утверждений. Отсюда рекомендация: обязательный якорь (sha / run-id / release) на каждое утверждение о сделанном.
7. Рекомендованы 8 штатных датчиков для H0/H1 (cost per resolved intent, оверхед пульта, доля дефектов без гейта, defect-escape, покрытие сигналом, self-churn, drift velocity, claim-anchor rate) — все считаются детерминированно, формулы готовы; телеметрию строить по OpenTelemetry GenAI semantic conventions.
