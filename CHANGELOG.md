- **P8 `user-journey-acceptance` — браузерная приёмка user-journey перед `done` (DEC-DEV-0225).** Новая fabric-ячейка `journey_acceptance` встаёт МЕЖДУ staging-деплоем (E.B `DEPLOYED`) и `done`: детерминированные Playwright-журнеи (`tests/uja/*.spec.ts`) прогоняются headless против живого staging-URL, вердикт (`PASS`/`FAIL`/`ENV_NOT_READY`) — байт-редукция по JSON-репорту через `orchestrator/lib/uja-report.cjs`, не суждение LLM. Закрывает разрыв «деплой зелёный + /health 2xx ≠ пользователь проходит поток» (живой прецедент: у пилота пост-логин падал в 404 при всех зелёных P6/P7/деплой). Диспетчеризуется существующей `/orchestrator:run user-journey-acceptance` (новых команд нет). Charter v6: PASS→`done`, FAIL→парковка `awaiting_journey_fix` (владелец ре-драйвит починку через `implementing`; гейт capture-don't-fix), ENV_NOT_READY→`runtime_gate_retry` (DoR-разрыв: `/integrator:add playwright`, нет журнеев, staging не 2xx). **Правило нуля-доказательств:** 0-журнейный репорт → `ENV_NOT_READY`, никогда не PASS. DoD-нога (`RL.md`): категория 3 требует UJA PASS на составе релиза (SSOT = P8 `run.json`), категория 5 для `has_ui` — journey-скриншоты как visual-conformance артефакт. Живой прогон VM-gated; prod-журнеи вне scope v0 (staging-only); Playwright MCP — позже.
