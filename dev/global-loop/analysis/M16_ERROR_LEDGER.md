# M16 — реестр собственных ошибок прогона

> **Зачем.** Требование владельца (2026-07-29, по ходу исполнения M16): ошибки исполнителя
> классифицировать и записывать **по ходу**, чтобы потом пересмотреть и распределить по артефактам и
> контурам принуждения. Ведётся вживую, не по памяти в конце.
>
> **Что сюда попадает:** мои ошибки как исполнителя пробы — не дефекты плеч (те идут в приёмку) и не
> находки о самой экосистеме (те в `REPORT.md`). Near-miss (поймал сам до ущерба) записывается тоже:
> он показывает, какое правило сработало.
>
> **Классы:** `destructive-on-shared` (разрушающее на общем ресурсе) · `env-trap` (грабля среды) ·
> `protocol` (отступление от пре-регистрации) · `measurement` (искажение самого замера) ·
> `near-miss`.

## ERR-01 · Уничтожил контейнеры рабочего пилота `docker compose up`-ом в клоне

| Поле | Значение |
|---|---|
| **Когда** | 2026-07-29 ~15:40 UTC+3, шаг 0.4 (подготовка стендов) |
| **Класс** | `destructive-on-shared` |
| **Severity** | Высокая: снесены живые контейнеры чужого (рабочего) сервиса |
| **Что сделал** | В клонах `~/m16/A` и `~/m16/B` выполнил `docker compose up -d postgres redis`, положившись на `docker-compose.override.yml`, который переопределял `container_name` и имена томов |
| **Что произошло** | Compose идентифицирует ресурсы по **имени проекта**, а оно бралось из `name: my-first-test` в основном compose-файле — то есть совпадало с проектом живого пилота. Compose счёл `mft-postgres`/`mft-redis` своими контейнерами сервисов `postgres`/`redis`, увидел смену `container_name` и **пересоздал их**: `mft-*` удалены, вместо них подняты `m16a-*`. Затем то же повторилось из клона B, снеся уже `m16a-*` |
| **Радиус ущерба** | Простой БД и Redis рабочего пилота ≈15 мин. Данные **не потеряны** (тома `my-first-test_*` не переиспользовались и не удалялись). Репозиторий пилота не тронут (HEAD `61c21f8`, тот же единственный untracked-файл). Процессы staging на 3000/3001 не падали |
| **Чем восстановлено** | `docker compose up -d postgres redis` из `~/projects/my-first-test` — вернул исходные имена, порты и тома. Проверено: 20 объектов схемы, `users=146`, Redis `PONG` + 14 166 ключей, `/health` → `{"status":"ok"}`. Страховка (дамп `pilot-db-backup.sql`, снят за 20 мин до инцидента) не понадобилась |
| **Корневая причина** | Применил разрушающую по своей природе команду к общему ресурсу **без dry-run**, хотя средство проверки существует и стоит одну команду: `docker compose config` показывает итоговые имя проекта, контейнеров и томов ДО применения. Ровно этой проверкой я потом и подтвердил исправление |
| **Что бы предотвратило** | Правило: перед `docker compose up` в клоне репозитория, чей compose-файл несёт фиксированные `name:` / `container_name:`, обязателен `docker compose config` + сверка полученных имён с `docker ps` живой машины |
| **Кандидат в enforcement** | **Дыра в существующем скилле.** `vm-factory-ops` §0 перечисляет разрушающие триггеры (`docker stop`, `kill-session`, `poweroff`, `snapshot restore`…), но `docker compose up` там **нет** — он выглядит созидательным. Предложение: (1) внести в §0 строку «`docker compose up/down` в клоне репозитория с фиксированными `name`/`container_name` = разрушающее для одноимённого проекта»; (2) добавить в §5 рецепт изоляции стенда: `name:` в override + проверка `docker compose config` перед `up`. Это дисциплина, а не код — детерминированного гейта на VM нет |
| **Влияние на замер** | Нулевое: оба плеча ещё не стартовали, приёмочный набор уже был закоммичен. Инвариант шва «рабочий пилот не мутировать» **нарушен мной** — фиксируется здесь и в `M16_RESULT.md`, а не заминается |
| **Статус** | Восстановлено и верифицировано; изоляция переделана на `name: m16a` / `name: m16b` с предварительной проверкой `docker compose config` |

## ERR-02 · `ffmpeg` съел скрипт, доставляемый через stdin

| Поле | Значение |
|---|---|
| **Когда** | 2026-07-29 ~15:42, создание фикстур |
| **Класс** | `env-trap` |
| **Severity** | Низкая: фоновая задача упала на середине, ущерба нет |
| **Что произошло** | Скрипт доставлялся на VM как `ssh ... 'bash -s' <<'EOF'` — то есть **через stdin**. Первый же вызов `ffmpeg` (который по умолчанию читает stdin) проглотил остаток текста скрипта; интерпретатору достался огрызок `60` от строки `mk fx-31min.mp4 1860` → `60: команда не найдена`, exit 127 |
| **Корневая причина** | Совмещение двух известных практик без учёта их взаимодействия: доставка скрипта через stdin (обход граблей кавычек PowerShell) + команда, читающая stdin |
| **Что бы предотвратило** | `ffmpeg -nostdin` либо `< /dev/null` на любой команде, читающей stdin, когда сам скрипт идёт через stdin |
| **Кандидат в enforcement** | Строка в `vm-factory-ops` §3 «Грабли ssh с Windows»: рядом с рецептом `bash -s` предупредить, что stdin занят телом скрипта — команды, читающие stdin (`ffmpeg`, `ssh`, `mysql`, `docker exec -i`, интерактивные CLI), обязаны получить `-nostdin`/`< /dev/null` |
| **Статус** | Исправлено, фикстуры созданы и проверены `ffprobe` |

| **Класс** | `measurement` (угроза достоверности замера) |

## ERR-05 · Стенды несли всю будущую историю, а протокол лежал в соседнем каталоге

| Поле | Значение |
|---|---|
| **Когда** | 2026-07-29 ~16:07, сразу после перезапуска плеча A |
| **Класс** | `measurement` |
| **Severity** | **Высокая** — при незамеченности обесценила бы весь эксперимент |
| **Что произошло** | Три канала утечки разом: (1) стенды сделаны `git clone` рабочего пилота с checkout на точку старта — то есть **вся будущая история в репозитории**: `git log --all` показывает коммиты вплоть до HEAD, `git show` отдаёт **готовую реализацию тех же FM-001/FM-002**, а `git remote -v` указывает прямо на пилот; (2) рабочие каталоги плеч были соседями (`~/m16/A`, `~/m16/B`) — один `ls ..` намекает на сравнение; (3) в том же `~/m16/` лежали `PROTOCOL/` с **обоими заданиями** и `ACCEPTANCE/` со **скрытым приёмочным набором** |
| **Как поймал** | Не проверкой, а взглядом на вывод `ls ~/m16` в собственной команде. То есть — случайно, второй раз подряд |
| **Что сделал** | Стенды пересобраны из `git archive 679f63a` в дерево **без истории**: свежий `git init`, ровно 1 коммит, 0 remote (проверено). Рабочий путь у обоих плеч один и тот же — `~/work/mvp` (плечи идут последовательно), в родительском каталоге нет ничего, кроме него. Весь операторский инструментарий уехал в скрытый `~/.m16/` (приёмка, протокол, шаблоны, карантин), калибровочная копия — в `~/.m16-calib` |
| **Что осталось непокрытым** | `~/projects/my-first-test` — рабочий пилот с готовой реализацией — двигать нельзя (общий ресурс, живой staging). Остаточный риск закрывается **детекцией**: после каждого прогона транскрипт сканируется на обращения за пределы `~/work/mvp`; находка = прогон помечается загрязнённым (пререга §10), а не аннулируется |

## ERR-06 · Приёмочный харнесс писал в базу рабочего пилота

| Поле | Значение |
|---|---|
| **Когда** | 2026-07-29 13:44–14:03, калибровка харнесса |
| **Класс** | `destructive-on-shared` |
| **Severity** | **Высокая** — записаны прикладные данные в живую БД чужого сервиса |
| **Что произошло** | Калибровочная мишень (копия пилота на HEAD) была поднята на своих портах со своей БД (`m16calib-postgres` :55403), и её собственные процессы действительно смотрели на 55403 — я это проверил. Но веб-приложение **проксирует `/api/*` на отдельный адрес**: `apps/web/lib/server-env.ts`, переменная `API_BASE_URL` со значением по умолчанию `http://localhost:3000`. Порт 3000 — это **живой staging рабочего пилота**, который пишет в `mft-postgres`. Я задал порты веба и API, но не адрес проксирования, поэтому весь трафик приёмки ушёл в пилот |
| **Как обнаружил** | Не проверкой, а расследованием: первый прогон дал «`201 Created`, но строки в БД нет». Ответ нёс `x-powered-by: Express` при том, что порт слушал Next.js — это и вывело на прокси |
| **Радиус ущерба** | В БД пилота создано: **20 пользователей, 29 сессий, 21 токен, 65 записей аудита**. Заданий локализации — **0** (пайплайн не запускался, деньги/провайдеры не тронуты). Ни одна существующая строка не изменена и не удалена |
| **Доказательство, что чужого не задето** | Все 65 записей аудита в окне имеют `user_agent` = `HeadlessChrome/151` (63) или `curl/8.5.0` (2); строк с любым другим агентом в окне — **ноль**. Последняя легитимная активность пилота — **2026-07-23 20:17**, за шесть дней до инцидента: staging простаивал |
| **Чем восстановлено** | Снят дамп состояния после инцидента (сохранён как свидетельство), затем транзакционное удаление ровно своего следа. Сверка с дампом, снятым **до** инцидента, сошлась по всем пяти таблицам: `users` 146, `sessions` 199, `auth_tokens` 73, `localization_jobs` 48, `audit_logs` 4482 |
| **Корневая причина** | Запустил **пишущий** харнесс по цели, не проверив, **куда именно попадает запись**. Изолировал хранилище и имена контейнеров, но не исходящие зависимости приложения. Одна канареечная запись с проверкой «легло ли туда, куда я думаю» стоила бы 30 секунд и поймала бы это до первого прогона |
| **Кандидат в enforcement** | **Встроено в харнесс как preflight** (не дисциплина): до первого сценария выполняется одна канареечная регистрация и проверяется, что строка появилась **в той БД, что передана флагом `--db`**. Не появилась → прогон останавливается с `write-path-mismatch`, а не «измеряет» неизвестно что. Защищает и оба плеча: их приложения точно так же могут иметь свой адрес по умолчанию |
| **Влияние на замер** | Прямого нет: плечи ещё не приёмились, их БД (`m16a`/`m16b`) не затронуты, прогон плеча A шёл в своей базе. Инвариант шва «рабочий пилот не мутировать» нарушен мной **второй раз** — фиксируется здесь и в `M16_RESULT.md` |
| **Статус** | Устранено, состояние восстановлено и сверено; калибровка перезапускается с явным `API_BASE_URL` |

## ERR-07 · Приёмка обращалась по `127.0.0.1`, а плечо настроено на `localhost`

| Поле | Значение |
|---|---|
| **Когда** | 2026-07-29 15:53, первый приёмочный прогон плеча A |
| **Класс** | `measurement` |
| **Severity** | Низкая — **поймано собственным preflight'ом до единого начисленного балла** |
| **Что произошло** | Харнесс шёл на `http://127.0.0.1:4100`, тогда как плечо задокументировало `http://localhost:4100` и настроило CORS ровно на этот origin. Браузерный Origin не совпал с allow-list → XHR регистрации до API не доходил, страница отдавала 200, а в БД не появлялось ничего |
| **Чем поймано** | Preflight, добавленный после ERR-06: «сервер принял, а в целевой БД пусто» → `write-path-mismatch`, прогон остановлен. Без него все 12 сценариев отработали бы вхолостую и дали бы правдоподобный, но полностью ложный ноль |
| **Исправление** | Базовый адрес берётся ровно тот, что плечо задокументировало о себе; правило записано в `02-adapter.log` и применено к обоим плечам одинаково |
| **Ценность записи** | Это первый случай, когда защита, построенная по следам предыдущей ошибки, **сработала на следующей же**. Аргумент в пользу тезиса отчёта: правило, материализованное в коде, ловит; правило-намерение — нет |

## Общий вывод по ERR-04 + ERR-05: не была построена модель поля зрения исполнителя

Обе ошибки — одна и та же: я готовил **репозиторий**, а надо было готовить **всё, что видит
исполнитель**. Изоляция проверялась там, где я о ней подумал (контейнеры, порты, тома), и не
проверялась там, где не подумал (история git, remote, соседние каталоги, пользовательские команды,
глобальный кэш экосистемы). Оба раза спасла случайность, а не процедура.

**Кандидат в enforcement — пред-прогонная инвентаризация «что видит исполнитель»**, обязательная для
любого контролируемого прогона (не только M16). Проверяемый список, каждый пункт даёт факт, а не
ощущение:

| Что проверить | Команда | Что считается провалом |
|---|---|---|
| История и происхождение репозитория | `git log --all --oneline \| wc -l`, `git remote -v` | видна история дальше точки старта; есть remote на источник |
| Рабочий и родительский каталоги | `ls -a ~/work`, `ls -a <cwd>/..` | видны артефакты эксперимента, соседнее плечо, протокол |
| Пользовательский уровень Claude | `ls ~/.claude/{commands,skills,agents,hooks}`, `cat ~/.claude/CLAUDE.md` | доступны команды/кэш изучаемого инструмента |
| Область MCP | `claude mcp list` в каталоге каждого плеча | сервер одного плеча виден другому |
| Что ещё запущено на машине | `docker ps`, `ss -tlnp` | доступен работающий экземпляр эталонной реализации |
| Скрытые каталоги оператора | `ls -a ~ \| grep -i <тег эксперимента>` | приёмка/протокол лежат на видном месте |
| **Исходящие зависимости самого стенда** (ERR-06) | `tr '\\0' '\\n' < /proc/<pid>/environ`; грепом по коду — `API_BASE_URL`, `*_URL`, `*_ORIGIN`, значения по умолчанию | приложение по умолчанию ходит на чужой адрес |
| **Куда реально ложится запись** (ERR-06) | одна канареечная запись → проверить, что строка появилась **в целевой БД** | запись ушла не туда, куда смотрит проверка |
