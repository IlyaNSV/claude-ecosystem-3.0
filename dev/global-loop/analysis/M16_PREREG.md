## 1. Вопрос и гипотеза

**Вопрос:** даёт ли канонический конвейер экосистемы (D2-Tech → реализация → гейты → деплой) измеримый
выигрыш по сравнению с сильным «голым» Claude Code при одинаковой поведенческой спецификации на входе?

**Гипотеза H1:** плечо с каноном даёт больше пройденных приёмочных журнеев и меньше дефектов при
бо́льших затратах токенов и времени.
**Нулевая H0:** различие в приёмке в пределах шума; канон отличается только ценой.

Заранее объявляю: **при n = 2–3 фичи это направление, а не доказательство**. Разница в разы —
сигнал; разница в проценты — шум.

## 2. Что уравнено, что различается

| Уравнено (одинаково у обоих плеч) | Различается (единственная переменная) |

| Формулировка задачи (побайтно одинаковый текст «что построить») | Инструментальная обвязка (MCP-набор у плеча B) |
| Окружение: одна VM, одинаковые версии, PostgreSQL + Redis, одинаковые внешние ключи | — |
| Модель исполнителя и уровень reasoning | — |
| Приёмочный набор (скрытый, один и тот же) | — |
| Отсутствие подсказок от меня во время прогона | — |

**Плечо A (канон):** репозиторий как есть на точке старта, включая `.claude/` и `CLAUDE.md`.
Исполнитель работает каноническими путями экосистемы.

**Плечо B (B2 — сильный контроль):** тот же репозиторий, из которого удалены `.claude/`, `CLAUDE.md`,
`.mcp.json` экосистемы; вместо них — минимальный `README.md` со стеком и командами запуска (чтобы
плечо B не проигрывало из-за незнания окружения, а не из-за отсутствия канона) + набор MCP-серверов
для веб-разработки. **Состав MCP определяется на шаге 0 добором из сети** (см. §8) — в него не входит
ничего из экосистемы.

## 4. Задача для обоих плеч

Текст задания — **побайтно одинаковый** для A и B, кроме одной вводной фразы про доступный
инструментарий. Задание формулируется так, чтобы не подсказывать процесс:

> «В репозитории есть продуктовая спецификация в `.product/`. Построй работающий MVP функциональных

Ни слова про эксперимент, про второе плечо, про способ работы и про то, как будет проверяться.

## 5. Приёмка: скрытый набор, написанный заранее

**До запуска обоих плеч** я пишу приёмочный набор по D2-B-спеке точки старта:

- 8–12 сценариев из `.product` (SC-*), переведённых в исполняемые проверки Playwright/API;
- каждая проверка привязана к идентификатору сценария или бизнес-правила из спеки;
- набор хранится **вне рабочих клонов обоих плеч** и не показывается исполнителям;
- набор фиксируется коммитом с временной меткой до старта прогонов — чтобы исключить подгонку под
  результат.

Приёмка запускается мной **одинаково** против обоих результатов, на одинаково поднятом окружении.

## 6. Метрики (формулы фиксируются здесь)

| Метрика | Формула | Комментарий |
|---|---|---|
| **pass^k** | доля приёмочных сценариев, пройденных во **всех** k попытках (k=2) | не pass@k: лучшая попытка не засчитывается |
| **spec-conformance** | доля проверяемых утверждений спеки (BR/IC/SC), реализованных фактически | считается по скрытому набору + ручной сверке |
| **дефекты после сдачи** | мой проход по обоим результатам одинаковым чек-листом | классификация по тем же классам, что в основном анализе |
| **токены** | сумма `output_tokens` по всем записям сессии **включая субагентов** | не `totalTokens` харнесса — он даёт пиковый контекст, а не расход (урок M13) |
| **wall-clock** | активное время (интервалы ≤15 мин) | как в основном анализе |
| **объём** | строки runtime / тесты / документация | разрез по тем же классам путей |
| **self-churn внутри прогона** | доля строк, переписанных внутри самого прогона | ловит хождение по кругу |

## 7. Ослепление и защита от конфаундов

1. **Исполнители не знают об эксперименте.** В задании нет ни слова о сравнении.
2. **Судья слеп.** Результаты обезличиваются (репозитории переименовываются в `RUN-X` / `RUN-Y`,
   история коммитов и следы инструментов вычищаются из того, что видит судья), порядок предъявления
   реверсируется, вердикт засчитывается только при совпадении обоих порядков.
3. **Скриптовая проверка идёт первой**, суждение — только там, где скрипт не решает.
4. **Порядок прогонов**: плечи идут последовательно на одной VM. Второе плечо может выиграть от
   «прогретого» окружения — это **неустранимо при n=1** и будет записано в ограничения, а не скрыто.
   Митигация: инфраструктура (БД, redis) поднимается заново для каждого плеча из одинакового состояния.
5. **Я не вмешиваюсь в прогон.** Любое моё сообщение исполнителю фиксируется в протоколе; допустимы
   только технические разблокировки (упавший контейнер), одинаковые для обоих плеч.

## 8. Шаг 0 — подготовка (до прогонов)

1. **Добор из сети (Informed Fetch)**: актуальный состав MCP-мастхэвов для веб-разработки под плечо B.
   Отдельно проверить **Claude Kitty** (мне неизвестен) и **GSD** — по нашему же ландшафтному ресёрчу
   от 19.07 GSD числился **BROKEN**; ставить сломанную обвязку в контроль нельзя, это подарит канону
   незаслуженную победу. Результат добора — с датами и ссылками, в отчёт.
2. **Подготовка стендов на VM**: два изолированных клона + раздельные порты и БД.
3. **Написание скрытого приёмочного набора** и его фиксация коммитом.
4. **Проверка занятости VM** (чужие сессии не трогаем) и снятие снапшота состояния до эксперимента.

## 9. Процедура прогона

1. Поднять стенд плеча A из точки старта → запустить сессию → мониторинг без вмешательства → фиксация
   финала (сессия сама объявляет завершение) → harvest транскрипта и состояния репозитория.
2. Погасить стенд A, поднять стенд плеча B из **той же** точки старта → те же шаги.
3. Прогнать скрытый приёмочный набор против обоих результатов, k=2.
4. Собрать метрики §6, провести слепое судейство §7.
5. Написать отчёт `M16_RESULT.md` с числами, ограничениями и честным «что этот замер не доказывает».

## 10. Стоп-правила

- Два системных сбоя подряд в одном плече → пауза и доклад владельцу (не «спасаю» плечо сам).
- Исполнитель запрашивает решение владельческого класса (деньги, продовый доступ, реальные секреты) →
  стоп, вопрос владельцу; ответ даётся **одинаково** обоим плечам.
- Обнаружение, что плечо догадалось об эксперименте → фиксирую в протоколе, прогон не аннулирую,
  но помечаю результат как загрязнённый.

## 11. Уборка после эксперимента (обязательна)

По завершении и **после** снятия всех результатов:

1. Транскрипты обеих сессий, оба итоговых состояния репозиториев и приёмочные отчёты — скопировать на
   хост в `vm-harvests/M16/` (это единственное, что переживает уборку).
2. На VM: погасить обе сессии поимённо, остановить и удалить контейнеры и тома стендов, удалить оба
   клона, удалить временные порты-форварды.
3. Проверить, что чужие сессии и рабочий пилот `~/projects/my-first-test` **не тронуты** (сверка HEAD
   до/после — фиксируется в отчёте).
4. Локальные рабочие копии на хосте (`PILOT-CLONE`, `VM-CORPUS`, `PILOT-DOCS`) — по решению владельца:
   удалить или оставить для воспроизводимости.
5. Итог уборки — отдельным разделом отчёта: что удалено, что сохранено, чем подтверждено.

## 12. Что этот замер не докажет

- При n = 2–3 фичи — **направление, не статистика**; доверительных интервалов не будет.
- Одна модель, одна предметная область, один день — переносимость на другие проекты не проверяется.
- Плечо B в конфигурации B2 сильнее «просто Claude Code», но слабее любой зрелой команды с CI/CD —
  сравнение честное только внутри объявленной рамки.
- Эффект «прогретой инфраструктуры» у второго плеча неустраним при одном прогоне.
