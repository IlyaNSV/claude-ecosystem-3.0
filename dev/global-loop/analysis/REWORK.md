# REWORK — характер работы 35 исполнительских сессий (RUN-A + RUN-B)

> **Вопрос, на который отвечает документ:** «не переписывает ли фабрика одно и то же по десять раз».
> **Единица анализа:** одна executor-сессия на VM (`cond-s1` … `cond-s35`).
> **Данные:** `DATASET/session_rework.csv` (построен вручную по брифам + журналу + машинным метрикам).
> **Источники:** брифы `vm-harvests/RUN-2026-07-17-A/prompt-s1..17.txt` и `vm-harvests/RUN-2026-07-22-B/prompt-s18..35.txt` · журнал `dev/global-loop/ASSIST_LOG.md` (записи RUN-A.1…A.38, RUN-B.1…B.58) · `DATASET/sessions.csv` (токены/время) · `DATASET/commits.csv` (коммиты с `cond_marker`).

---

## 1. Метод

Каждая сессия классифицирована **по основному содержанию работы**, а не по заголовку журнальной записи (заголовки писала та же сторона, которая себя оценивала). Опора — текст брифа (что поручалось) + итоги в журнале + коммиты.

**Кодировка колонок `class` / `secondary_class`:**
- `class` — ведущий класс. Если два класса дают примерно равный вклад — `MIXED`, а оба класса перечислены в `secondary_class` через `+`, **ведущий первым**.
- Если класс один, но есть заметная второстепенная составляющая — она указана в `secondary_class` (расширение рубрики; сделано, чтобы не терять информацию: 12 из 35 сессий имеют реальную вторую компоненту).
- Во всех агрегатах ниже «ведущий класс» = `class`, а для `MIXED` — первый элемент `secondary_class`.

**Что считается «переделкой»:**
- **строгая мера** — ведущий класс ∈ {`REWORK_DEFECT`, `REWORK_PROCESS`, `RECOVERY`};
- **широкая мера** — любой из этих классов присутствует в ведущем **или** вторичном.

## 4. Цепочки переделок — кто кого переделывал

16 сессий из 35 несут непустой `redoes_session`. Ниже — связные цепочки.

### Ц1. Гейт-петля RUN-A: один и тот же состав фич через четыре раунда P6
```
s2 (P6-батч ×6 FM) ──погибла от ребута хоста──►
s3 (перезапуск батча, capture-only) ──5× NO-GO──►
   ├─ s4 (husky→beads: механический корень всех пяти NO-GO)
   ├─ s5 (consilium по эскалированным развилкам)
   └─ s6 (fix-итерация ратифицированного пакета)
s7 (P6 round-2, те же 5 FM) ──3× MANUAL_VERIFY + 1 NO-GO──►
   ├─ s8 (построен отсутствовавший Lighthouse-гейт)
   └─ s9 (fix-волна из 3 ратифицированных фиксов)
s13 (P6 re-gate round-final, те же FM) ──умерла на session-limit после 4/6──►
s14 (добивка round-final) ──0 NO-GO──► гейт закрыт
```
**Цепочка из 5 сессий по прямым рёбрам `redoes` (s2→s3→s7→s13→s14) — самая длинная в прогоне.** Одни и те же 5–7 фич прогонялись через P6 **четыре раза**. Вся петля вместе с обслуживающими fix-сессиями = 10 сессий, **3 651 446 токенов (24.6%)** и 353.6 активных минут (22.5%). Только гейт-раунды (без фиксов) — 2 521 413 токенов (17.0%).

Важная деталь: раунды **не были** бессмысленным повторением. Round-1 нашёл один механический корень и 5 содержательных дефектов; round-2 после фиксов дал 1 GO и вскрыл 3 owner-class развилки; round-final подтвердил 0 NO-GO. Это сходящаяся, а не циклящаяся петля. Но цена сходимости — четверть прогона.

### Ц2. FM-004: построена, потом транспорт переписан
```
s10 (P5 FM-004) ──убита kill-ом кондуктора на 12/23 задач──►
s11 (достройка с задачи 4.2, не рестарт) ──построен BullMQ-Worker по design.md──►
s12 (транспорт переписан BullMQ → ioredis-RPUSH по ратификации владельца)
```
3 сессии, **2 400 073 токена (16.2%)**. Здесь переделка настоящая: транспорт, только что построенный по букве `design.md`, был конвертирован целиком, потому что ратифицированное решение (консистентность с FM-002) противоречило спеке. Дефект-класс — расхождение спеки и as-built, известное до стройки (FM-002 уже ездил на ioredis), но не снятое до старта P5.

### Ц3. Демоушен FM-004 туда и обратно
```
s17 (демоушен: FM-004 real-path MUST→SHOULD, FB-013 → RL-002; 3 docs-коммита)
   ├─ s18 (bring-forward: FB-013 возвращён в RL-001 — отмена решения s17)
   └─ s21 (frontmatter: priority should→must, release_split снят — отмена правки s17)
```
Чистый round-trip документов: владелец за двое суток отменил собственную ратификацию. Объём мал (десятки строк), но это единственный пример в прогоне, где работа была **полностью аннулирована**, а не улучшена.

### Ц4. UI/приёмка RUN-B — самая длинная цепочка «зелёный вердикт → находка владельца → фикс»
```
RUN-A.38 владелец смотрит UI: «нет стилизации, просто html»
   └─ s22 (CSS-слой построен, Lighthouse ~1.00, DoD не мигнул)
владелец проходит руками: 3 навигационные дыры мимо всех гейтов
   └─ s28 (построена и валидирована новая приёмочная нога UJA; поймала 3 known + больше)
   └─ s29 (фикс web-слоя по показаниям UJA → UJA PASS 3/3)
владелец проходит руками ВТОРОЙ раз: 2 новые дыры мимо зелёного UJA
   └─ s30 (матрица доступа + P2028 + logout + UJA v2 → PASS 7/7)

владелец проходит руками ТРЕТИЙ раз: чип-тупик, пустой dashboard, нет admin-учётки
```

8 сессий, **3 597 447 токенов (24.3%)**, 422.9 активных минут (26.9%). Только ремонтная часть (s29, s30, s31) — 2 042 229 токенов (13.8%).

Это самый дорогой и самый диагностичный участок. Механизм повторения здесь **не** «фабрика забыла и переписала»: каждый следующий круг чинил **другой** класс дыр, который предыдущий гейт по построению не видел (функциональные тесты не видят презентацию → UJA не видит негативные журнеи → негативные журнеи не видят cross-realm). Приёмка расширялась под каждую находку post-hoc — четыре раза подряд.

## 5. Прямой ответ на вопрос владельца

**«Переписывает ли фабрика одно и то же по десять раз» — нет.** Ни один артефакт не переписывался более трёх раз, и повторные проходы почти всегда были **сходящимися**, а не циклическими: каждый раунд закрывал класс проблем и находил следующий, отличный от предыдущего.

**Но:** от 21% до 55% ресурса прогона (в зависимости от того, считать ли смешанные сессии) ушло не на первое построение. Три отчётливых источника:

1. **Гейт-петля (24.6% токенов).** Четыре раунда P6 по одному составу фич. Первый раунд поймал ОДИН механический корень (`husky→beads`), обрушивший все пять вердиктов сразу — то есть 5 из 5 NO-GO round-1 были одной ошибкой, продиагностированной пятикратно. Это самая явная неэффективность прогона.
2. **Пост-hoc расширение приёмки (24.3% токенов).** Владелец находил руками то, чего не видел ни один зелёный гейт — четыре раза подряд, каждый раз новым классом. Приёмка достраивалась после факта.
3. **Обрывы (17.5% токенов в сессиях s3/s11/s14).** Три сессии существуют только потому, что предыдущие умерли: ребут хоста (s2), преждевременный kill кондуктора по ложному сигналу монитора (s10), session-limit VM-аккаунта (s13). Один из трёх обрывов — **ошибка самого кондуктора**, не инфраструктуры.

Единственный случай **полного аннулирования** работы за весь прогон — демоушен FM-004 (s17), отменённый владельцем через двое суток (s18/s21). Единственное **нарушение канона**, потребовавшее отдельной сессии-догона, — s30 → s31 (3.3% токенов).

## 6. Границы оценки

Читать цифры выше следует с этими оговорками — они существенны.

1. **Классификация — суждение, а не измерение.** Границы `NEW` / `REWORK_DEFECT` размыты по построению: s29 «строила страницы, которых не было» и одновременно «чинила пять root-cause багов». s9 «чинила по эскалациям» и одновременно впервые построила worker-drain. Разные аналитики получат ±3–4 сессии в любом классе. Именно поэтому даны две меры (строгая/широкая), а не одна.

2. **`MIXED` — 5 сессий, и их отнесение по «ведущему элементу» смещает распределение.** s4 и s30 при обратном прочтении уедут в `NEW`, и строгая доля переделок упадёт с 22.9% до 17.1%.

3. **`VERIFY` — не значит «бесполезно».** 9 сессий класса `VERIFY` (26.8% токенов) не меняли продукт, но именно они породили весь список дефектов. Считать их накладными расходами нельзя; считать полезной работой в смысле «построено новое» — тоже.

4. **Цифра «60.5% токенов на не-плановую работу» завышает проблему.** В триггер `гейт` попали и штатные раунды DoD-цикла (s13 — плановый round-final, s5 — штатный consilium): гейт-раунд по спецификации процесса **является** плановой работой. Честнее читать так: 17.5% — обрывы, 12.9% — находки владельца, 3.3% — нарушение канона; остальное — процессная норма, часть которой избыточна.

5. **Токены сессии ≠ цена переделки.** Для s3, s11, s14 в таблицу вошёл **весь** объём сессии, включая продуктивную часть. Реальная цена обрыва меньше: s11 достраивала FM-004 с задачи 4.2, а не перестраивала 12 готовых. Число 17.5% — верхняя граница, не оценка потерь.

6. **По `cond-s2` нет машинных метрик.** VM умерла до harvest, транскрипт не снят. Сессия учтена в счёте (35), но её токены и минуты отсутствуют во всех суммах — то есть цена гейт-петли Ц1 занижена на неизвестную величину (по журналу — порядка часа работы и одного FM с ремедиацией).

7. **`commits.csv` размечен `cond_marker` только с s13.** Для s1–s12 связь «сессия → коммит» восстановлена по журналу, а не машинно. Объёмные метрики коммитов (`ins`/`del`/`runtime_lines`) для ранних сессий не использовались.

8. **Часть работы дублирована вне executor-слоя.** Задачи 3–4 брифа s32 были параллельно исполнены хост-сессией (коллизия двух кондукторов, `ASSIST_LOG` RUN-B.44) — s32 распознала already-done и не продублировала, но бриф был написан на уже сделанное. Это форма переделки, не попавшая ни в один класс рубрики.

9. **`wall_active_min` — активное время executor-сессии,** без времени кондуктора на разбор/бриф/дизпатч (в журнале это отдельные `attention: ~N мин`, суммарно сопоставимые величины) и без времени владельца на ручные проходы (RUN-B.26 — 40 мин, RUN-B.34 — 30 мин, и т.д.).

10. **Смотреть на «переделку» как на чистую потерю неверно.** Часть повторов — спроектированный remediation-цикл P6 (владелец сам ратифицировал «сток с ремедиацией» вместо capture-only на RUN-A.8, сознательно выбрав больше циклов внутри сессии ради меньшего числа сессий).
